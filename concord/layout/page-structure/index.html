Page Structure

Page structure starts with meaning, intended reading order, and native HTML landmarks. Define the page hierarchy before deciding width, spacing, columns, or responsive placement; layout can then adapt presentation without changing what the content is or how it should be understood.

Layout contract

Semantic structure comes before geometry

Start with meaning and intended reading order. Define the page’s semantic hierarchy first, then let layout change geometry without changing what the content is or how it should be understood.

Start with three decisions

Define what the content is and how it should be understood before choosing geometry.

  1. 01
    Meaning Identify navigation, primary content, supporting content, and page-level information.
  2. 02
    Order Arrange content in the sequence in which it should be understood and operated.
  3. 03
    Layout Use available space without redefining the hierarchy established by meaning and order.

Semantic HTML shell

The anatomy above and the markup below describe the same hierarchy. The numbered path represents meaningful source and reading order, not a fixed desktop arrangement. In this example, primary navigation is intentionally nested inside the global header; `nav` may live elsewhere when the page architecture requires it.

HTML 
<header>
  <nav aria-label="Primary">...</nav>
</header>

<main>
  <section aria-labelledby="page-title">
    <h1 id="page-title">Page title</h1>
    ...
  </section>
  <aside aria-labelledby="supporting-title">
    <h2 id="supporting-title">Related information</h2>
    ...
  </aside>
</main>

<footer>...</footer>

Landmark rules

Use document semantics to express meaning; do not translate every visual box into a landmark.

  • Native landmarks first — use `header`, `nav`, `main`, `aside`, and `footer` for their semantic purpose instead of recreating native meaning with redundant ARIA roles.
  • One primary main — a document should ordinarily expose one `main` landmark for the page's primary content.
  • Name repeated landmarks — when multiple landmarks of the same type need distinction, give them clear accessible names.
  • Sections are intentional — use `section` for a meaningful thematic grouping, and associate it with a visible heading when it should be exposed as a named region.
  • Order remains meaningful — responsive layout should preserve source, reading, and keyboard order that still makes sense when visual placement changes.

Layout comes after structure

Once meaning and order are established, use the smallest layout mechanism that expresses the required geometry. Content Boundary, Sections & Regions, Grid, and Layout primitives decide spatial behavior; Page Structure keeps the document hierarchy stable as that geometry changes.

Page shell vs. Template

Page shell — the recurring structural relationships that persist across pages: global header, primary navigation when appropriate, main content, optional supporting content, and footer.

Template — a recognizable product- or task-specific composition such as a Dashboard, Settings Page, or Detail Page. It combines the shell with Components, Patterns, content hierarchy, and task-specific intent.

The shell defines what persists. A Template defines which product page is being composed.
