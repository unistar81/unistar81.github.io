LAYOUT

Sidebar

Sidebar is an asymmetric two-region composition. A flexible main region and a narrower supporting region stay beside each other while local space can satisfy both sizing roles. When that relationship no longer fits, the same two direct children stack in source order.

Layout contract

Main content keeps priority while supporting content adapts beside it

One parent owns two unequal spatial roles. The main region protects a useful minimum width, the supporting region starts from a preferred width, and the same source-ordered children stack when local space can no longer satisfy both.

SIDEBAR RELATIONSHIP

One main region. One supporting region. One local-width relationship.

The markup and sizing rules stay the same. Only the inline space supplied by the containing composition changes.

Flexbox owns two unequal spatial roles

Use Sidebar when one parent owns exactly two spatial roles: a flexible main region followed by supporting content. The first and last child positions establish sizing behavior; they do not assign document meaning.

The semantic elements remain a content decision. An aside is appropriate only when the second region is genuinely complementary to the surrounding content.

HTML 
<div class="dsl-sidebar">
  <section>Main content</section>
  <aside>Supporting content</aside>
</div>

Stacking follows local available width

Sidebar does not ask whether the viewport is a phone, tablet, or desktop. It responds to the inline space its own parent provides.

The side-by-side state remains possible while local width can satisfy the main region's minimum useful width, the parent-owned gap, and the sidebar's preferred width. When those requirements no longer fit together, Flexbox wraps the same children onto separate rows.

The stacking point is therefore a consequence of the relationship, not a separately authored breakpoint.

Main and sidebar have different sizing roles

The first child grows into remaining space while protecting --dsl-sidebar-content-min-inline-size. The last child starts from --dsl-sidebar-inline-size and can grow when it occupies a line by itself.

Those roles are intentionally asymmetric. Sidebar is not a generic two-column system, and consumers do not need matching width classes on the children.

Public configuration

Sidebar exposes three relationship-level custom properties. Set them on the .dsl-sidebar that owns the main + supporting-region relationship.

Gap --dsl-sidebar-gap
Space between the two regions, including after the relationship wraps. Default · semantic layout content gap · 24px fallback
Sidebar preferred width --dsl-sidebar-inline-size
Preferred inline basis for the second direct child. Default · 18rem
Main minimum useful width --dsl-sidebar-content-min-inline-size
Minimum inline size the first direct child protects before the relationship wraps. Default · 30rem

Internal --_dsl-* properties and Flexbox growth values are implementation details, not public API. Both child minimums still clamp to the available width so very narrow containers can remain resilient.

Use Sidebar when one region supports another

Good uses include a filter rail beside results, related actions beside a working surface, metadata beside an article, a local table of contents beside documentation, or supporting controls beside a primary task.

The important requirement is the relationship: one substantial main region and one narrower supporting region that may stack when local space becomes insufficient.

Choose Split or Grid when the relationship differs

Use Split when two peer groups should move to opposite inline edges and wrap according to their combined intrinsic size. Split does not protect a main-content minimum or assign the other group a preferred sidebar width.

Use Grid when several regions need coordinated tracks, explicit placement, or shared alignment. Do not choose Sidebar merely because something happens to appear on the side.

Geometry does not assign semantics or page structure

.dsl-sidebar controls geometry only. Its children might be a main, section, article, aside, nav, or neutral wrapper depending on the surrounding document.

Do not add an aside or navigation landmark solely because a region is visually narrow. Likewise, persistent application navigation, coordinated shell transitions, and multi-region page architecture may belong to Grid, a Pattern, or a Template rather than this primitive.

Preserve source order and content resilience

The stacked state follows DOM order: the first child remains first and the supporting region remains second. Author meaningful reading and focus order before applying the layout.

Both regions still own their internal wrapping, localization, zoom, minimum sizing, and content growth. Do not force fixed heights or fixed descendant widths merely to preserve the side-by-side state.
