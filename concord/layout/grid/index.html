LAYOUT

Grid

Concord Grid is a repeating-track layout primitive for collections whose siblings benefit from shared columns and rows. Its default is intrinsic: local inline size and a useful minimum item size resolve the track count without device columns, viewport breakpoints, or layout JavaScript.

Layout contract

Available space resolves the track count

Grid defines a repeating track relationship. By default, a useful minimum item size and local inline space determine how many tracks fit without viewport breakpoints or layout JavaScript.

Intrinsic tracks are the default

The default behaves like `repeat(auto-fit, minmax(...))`. As available inline space changes, the browser continuously resolves how many tracks fit. The same Grid can therefore move from three tracks to two to one without a media query or container-query threshold.

HTML 
<div class="dsl-grid">
  <article>...</article>
  <article>...</article>
  <article>...</article>
</div>

Documentation JavaScript changes only the preview width and minimum-item test value. It does not calculate tracks or rearrange items.

The minimum yields to the container

`--dsl-grid-min-item-size` is a useful preferred lower bound, not permission to overflow a narrower container. Concord's implementation clamps that minimum against `100%`, so a single track can shrink to the space it actually receives when the container is narrower than the preferred item size.

This keeps the primitive resilient in narrow regions while still allowing the minimum item size to govern when another track can fit.

Public configuration

Grid exposes four public custom properties. Tune the relationship at the owning composition; do not turn these values into a breakpoint-specific utility API.

Minimum item size --dsl-grid-min-item-size
Preferred lower bound used while resolving intrinsic tracks. Default · 16rem
Column gap --dsl-grid-column-gap
Space between adjacent columns, resolved through the semantic layout content gap.
Row gap --dsl-grid-row-gap
Space between rows. By default it follows the resolved column gap so both axes stay coordinated.
Track mode / count --dsl-grid-columns
Defaults to auto-fit. An owning composition may provide an explicit count only when that fixed track relationship is intentional.

Explicit track counts are an escape hatch

An explicit count changes ownership: the composition is now asserting that three tracks matter. It must also remain valid when the available space cannot comfortably support that relationship. Do not use a fixed count as a substitute for the intrinsic default or as a device-column API.

CSS 
.featured-grid {
  --dsl-grid-columns: 3;
}

Grid is not a utility matrix

Concord does not publish breakpoint-specific `span-*`, `offset-*`, or device-column class families. Deliberate spans, named areas, and asymmetric placement belong to the composition documented in Placement & Spans rather than to a global utility matrix.

Content quantity and editorial hierarchy also belong above Grid. A one-item, two-item, or featured collection may legitimately need a different composition because content strategy changed; that belongs to a Content Collection or Featured Collection Pattern rather than the generic Grid primitive.

Choose Grid when siblings need shared tracks

Use Grid when a collection benefits from a repeating track system: sibling items should align to common columns or rows, and available space should determine how many tracks fit.

Do not reach for Grid merely to place a few inline peers next to each other or to add vertical rhythm. Those relationships are usually better expressed by normal flow, Cluster, Flow, Split, or another smaller primitive.

Preserve meaningful source order

Grid can change geometry without changing document meaning. Keep DOM and focus order meaningful, especially when an owning composition adds explicit placement or spans. Do not use visual placement to create a reading sequence that conflicts with source order, keyboard navigation, or assistive-technology traversal.
