Viewport Breakpoints

Viewport breakpoints are width thresholds for coordinated macro shell changes, not a catalog of device names. Concord keeps them secondary to intrinsic and container-aware composition because reusable content usually responds more truthfully to its own available space.

Layout contract

A viewport breakpoint is a coordinated shell transition

Use a viewport-width threshold when page-level architecture must change together. Local compositions remain intrinsic or container-aware.

A viewport breakpoint belongs to the page shell

Use a viewport breakpoint when page-level architecture must change together. A persistent navigation rail may become a trigger and overlay, the global header may change navigation architecture, or a multi-region Template may collapse into a simpler shell. Those are viewport-owned transitions.

A phone-sized viewport does not activate a special `mobile` mode in Concord. It simply crosses any shell thresholds whose behavior conditions are met. Inside that compact shell, reusable components and compositions still use normal flow, intrinsic sizing, and container-aware behavior based on the space they actually receive.

Choose the threshold from the transition

Start from the working page architecture and resize until that architecture no longer preserves its intended relationships or operability. The threshold belongs near the point where the alternate shell becomes necessary.

Validate the transition with real navigation labels, long content, localization, zoom, and changed writing direction. The number documents a behavior boundary; it does not identify a phone, tablet, laptop, or hardware class.

Keep the threshold with the shell

A viewport threshold should live with the page shell or Template that owns the transition. This example value is illustrative, not a Concord breakpoint token:

The value can differ for another shell when its architecture fails at a different point. Reusable descendants should not inherit this number as their own responsive API.

.application-shell {
  /* persistent shell */
}

@media (max-width: 62rem) {
  .application-shell {
    /* compact shell */
  }
}

Preview widths are test conditions

Documentation widths such as 320, 480, or 768 are sampling points. They help exercise narrow and intermediate conditions, but they are not automatically Concord breakpoints.

When a real shell threshold exists, test the shell just above and just below that threshold as well as at useful extreme widths. A preview preset and a breakpoint answer different questions.

A media query is not automatically a breakpoint

This page is about viewport-width breakpoints. Other media features such as reduced motion, forced colors, orientation, or input characteristics describe environment or capability conditions. They should not be folded into a width breakpoint scale merely because they also use `@media`.

Concord does not publish a global breakpoint scale

Concord currently has no global breakpoint tokens or phone / tablet / desktop aliases. Keep a viewport threshold with the page shell or Template that owns the transition.

Promote a threshold into a shared system contract only when repeated macro behavior across multiple shells proves that the same boundary is genuinely stable. If that happens, document the coordinated behavior and ownership rather than turning the value into a device label.

Keep shared thresholds sparse, not artificial

A small set of proven shell thresholds is easier to govern than overlapping arbitrary ranges. But do not force unrelated shell transitions onto one value merely to make the scale look tidy. Shared values should represent shared behavior.

Preserve meaning across shell states

A viewport breakpoint can change geometry and interaction architecture without changing what the page means. Preserve landmarks, accessible names, essential actions, and meaningful DOM and focus order. If persistent navigation becomes an overlay or drawer, provide an accessible trigger and appropriate focus behavior rather than removing access to the navigation.
