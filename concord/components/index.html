Component architecture

A component is a contract, not a wrapper.

The visible component is one expression of a larger system contract. Concord keeps semantics, expression, behavior, and delivery distinct enough to evolve without fragmenting the design language.

Shared visual intent remains upstream. Component tokens own only the decisions that belong specifically to the component.

01 / Semantics

Native structure preserves meaning.

Buttons remain buttons, inputs remain inputs, and accessible names, relationships, and browser semantics exist before a packaging or framework layer is introduced.

02 / Expression

Tokens govern component-owned decisions.

Shared semantic roles stay upstream while component tokens own implementation decisions such as state, geometry, and approved visual treatment. Theme and density can change expression without rewriting structure.

03 / Behavior

Browser behavior before abstraction.

Native interaction models remain the baseline. JavaScript adds explicit component behavior only where the interface contract requires state or interaction beyond what semantic HTML already provides.

04 / Delivery

Delivery layers consume the same contract.

Canonical HTML/CSS remains first-class, Web Components package the same underlying contract, and framework adapters provide integration without redefining semantics, tokens, styling, or behavior.

Choose the owner

Escalate only when the responsibility changes.

Reuse the smallest Concord layer that can own the contract coherently. A larger composition does not automatically require a larger component.

  1. 01 · Component One reusable interface contract Own semantics, approved expression, state, behavior, and accessibility for one interface.
  2. 02 · Pattern A recurring relationship among contracts Compose existing Components and Layout to solve a recurring user problem without rewriting their internals. Patterns overview ↗
  3. 03 · Template A repeatable page-scale arrangement Own regions, hierarchy, source order, responsive relationships, and placement of existing contracts. Templates overview ↗
  4. 04 · Application Product and domain responsibility Keep routing, data, permissions, persistence, workflow state, and business rules with the consuming product. Ownership model ↗

Do not create a Component merely to package a workflow relationship, page layout, or product-specific state.
