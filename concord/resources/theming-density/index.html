Theming & Density

Theme, appearance, and density are independent axes applied to one governed token graph. Theme changes visual language, appearance changes the luminance environment, and density changes spatial character without multiplying component markup or creating parallel token systems.

Architecture thesis

Three independent axes. One shared contract.

Variation belongs in approved token boundaries, not in duplicated component implementations.

On the web, Concord composes three selector-driven axes:

The same Semantic and Component contracts remain in use in every combination.

01 · Theme Visual language

Palette, typography, geometry, elevation, and approved component expression.

Variation is expressed by rebinding token contracts rather than by branching component markup or maintaining parallel implementations.

Override governance

Variation is allowed only inside explicit ownership boundaries

Theme and density sources are configured with `allowedTiers: ['system', 'semantic', 'component']`.

Foundation is intentionally outside their configured override boundary.

That permission is a maximum architectural boundary, not a requirement that every override source modify every allowed tier. Authored overrides should still live at the tier that owns the decision.

The dark appearance source is narrower: it is applied only at the Semantic tier. Themes provide the System-level dark appearance roles that preserve each theme's personality, while Appearance remaps stable Semantic color intent onto those theme-owned roles.

Allowed does not mean required.

The configured tier list is the outer permission boundary. An authored override should still live at the tier that actually owns the decision; it should not descend into Component simply because the configuration permits it.

Web cascade

Orthogonal modes compose without resetting one another

The web cascade is:

`base → theme → density → appearance → consumer overrides`

Theme, density, and appearance output is sparse and ownership-bound. Scoped styles contain authored overrides plus only the dependent aliases needed to make the active scope recompute correctly. Absence means preserve the upstream contract; an override is not a reset opportunity. A required exported interface may still require an explicit role declaration even when its value matches the base contract; those narrow completeness requirements are validated separately from ordinary overrides.

This matters because orthogonal modes must not reset one another. A density selector changes approved spatial dimensions without re-emitting or replacing theme-owned typography, stroke weight, color, or shape. Appearance can remap luminance while preserving the active theme's System-level palette.

Current tests explicitly verify that density output changes approved spatial dimensions without re-emitting unrelated brand or action colors or replacing theme-owned typography, stroke weight, or shape.

Appearance boundary

Dark mode remaps intent; it does not duplicate components

Appearance answers whether the current web environment is light or dark.

The generated appearance layer uses `data-appearance="light"` and `data-appearance="dark"` and rebinds the authored alias graph at theme, appearance, and density boundaries. It does not require a second component implementation, runtime token compilation, or a separate dark copy of component CSS.

Theme files are validated to provide the dark System color roles required by the Semantic dark appearance mapping.

Density boundary

Density is additive; it is not another size-variant matrix

Density and component size are separate decisions.

Compact and Spacious change approved spatial dimensions while a Button remains the same `medium` size variant. Current density tests verify that padding, gaps, control footprint, and minimum sizes can change while typography, stroke weight, color, and theme-owned shape remain stable.

This keeps density additive rather than multiplying every component variant by every density mode.

Accessibility environments

User contrast settings sit outside the brand matrix

Forced colors are an accessibility environment, not a brand theme.

`forced-colors: active` uses platform/system colors and must preserve boundaries, focus, state, and meaning rather than replacing the user's palette with a branded high-contrast theme.

`prefers-contrast: more` is separate progressive enhancement. Neither belongs in the Theme or Density registry.

Forced colors User-selected system palette

Preserve boundaries, focus, state, and meaning with CSS system colors rather than introducing a branded “high-contrast theme.”

More contrast Progressive enhancement

prefers-contrast: more is separate from Theme, Appearance, and Density.

Governance rule

Fix the ownership defect, not the specimen

When a theme, density, or appearance exposes a contrast, inheritance, or ownership defect, fix the token contract or generator boundary. Do not patch documentation-only CSS or create a local component variant to hide the architecture problem.
