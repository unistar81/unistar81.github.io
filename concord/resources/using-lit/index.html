Using Lit

Lit Web Components are Concord’s Web Component delivery implementation. They provide custom-element APIs over the same semantic HTML, external CSS, token, accessibility, and behavior contracts used by the platform-native path.

Web Component delivery

Custom-element ergonomics over one shared contract

Lit is a delivery layer, not the owner of the design language.

Shared system contract HTML + CSS + tokens + behavior Already defined before Lit enters the delivery path

Start here

Register explicitly, then consume the adapter

Concord’s Lit package is a private workspace package. The repository verifies it with pnpm build:lit, and importing the package alone does not register elements.

  2. 02
    Register intentionally

    Call the exported defineDsl* function; package import has no registry side effect.

  3. 03
    Use the custom-element API

    Configure component-owned properties while the rendered native element keeps its semantics.

Registration contract

Imports are inert until you choose a tag

Custom-element registration stays explicit so application startup, tag naming, and package loading remain separate decisions.

  1. 01 Side-effect-free imports

    Importing @dsl/components-lit must not mutate the CustomElementRegistry;

  2. 02 Explicit component registration

    Each component exports a defineDsl* registration function;

  3. 03 Canonical tag defaults

    Definition functions use the canonical dsl-* tag by default;

  4. 04 Configurable registration

    Registration can accept a different tag name where the component implementation supports it;

  5. 05 Independent naming systems

    Custom-element tag naming remains separate from CSS class and token-variable prefixes.

Tag naming is not CSS naming.

A custom-element name must contain a hyphen, but that does not make the tag prefix the owner of component classes or token-variable prefixes.

Rendering model

Light DOM keeps the shared CSS contract intact

Light DOM is the default integration model so Concord’s authored external CSS remains the styling implementation.

The consuming document remains responsible for loading the shared token, core, icon, and component stylesheets. Lit must not embed, clone, fetch, or redefine component CSS.

Shadow DOM requires an explicit component-level architecture decision because the canonical global CSS contract does not cross a shadow boundary automatically.

01 Default

Light DOM

Canonical classes remain visible to the same authored component stylesheets.

02 Application responsibility

Load the shared CSS

Tokens, core, icons, and component CSS stay outside the Lit implementation.

03 Exception

Shadow DOM requires a decision

Do not introduce a shadow boundary without an explicit component-level architecture reason.

Host architecture

The Lit API does not choose the canonical static host

A Lit custom-element API and the canonical static HTML host are related but separate architectural decisions.

For native-host components, Lit can expose a custom-element delivery API while rendering the canonical native element inside it. Button is the reference pattern: `<dsl-button>` renders a native `<button class="dsl-button">` in light DOM, preserving native activation, form semantics, disabled behavior, and focus behavior.

Progressive upgrade

Authored light DOM and managed rendering can coexist

Canonical custom-host components must support progressive adoption.

When a consumer has already authored canonical light DOM inside an approved custom host, upgrading that element must preserve the authored content rather than replace it.

When Lit or a framework adapter creates an empty host, the component may render managed light-DOM anatomy from its adapter properties.

Card is the current reference pattern: it distinguishes authored light DOM from managed rendering so the same custom-element identity can support static authoring and adapter-driven delivery without duplicating the component root.

Same component identity Two valid initialization states

The host starts with authored content or without it; the component contract stays the same.

Authored host Existing light DOM is preserved.

A consumer-authored canonical custom host upgrades without replacing the content already inside it.

Empty adapter-created host Lit may render managed anatomy.

Adapter properties can populate the same component identity when no authored child structure exists.

API ownership

Expose component decisions, not a duplicate browser API

Lit properties and attributes should expose the shared component contract rather than reproduce the entire native DOM API.

Use properties for component-owned state and configuration. Keep native child elements responsible for native semantics and browser behavior where composition can preserve those responsibilities.

Button’s Lit adapter currently exposes component-level properties such as label, variant, size, disabled, icon placement, and accessible naming while rendering the native button that owns activation and form behavior.

01 · Component-owned API Button adapter

label · variant · size · disabled · icon placement · accessible naming

02 · Native semantic owner Rendered button

activation · form semantics · disabled behavior · keyboard/focus behavior

System concerns

Theme and density stay outside the adapter

Theme, appearance, and density remain system-level token concerns.

The Lit adapter consumes the same inherited CSS custom-property environment as HTML/CSS. Do not create Lit-specific theme state, duplicate token contracts, or framework-owned visual values.

01 · Tokens Inherited CSS custom properties
02 · Theme / appearance System-level selectors and generated mappings
03 · Density Shared token overrides
04 · Lit consumes The resulting system environment

Architecture proof

The Web Component layer gives applications reusable custom-element APIs without turning Lit into a second design system. The same component contract remains consumable through HTML/CSS, Lit Web Components, and framework adapters.
