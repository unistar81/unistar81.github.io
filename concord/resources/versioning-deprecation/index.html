Versioning & Deprecation

Versioning communicates consumer impact. Deprecation creates a compatibility period in which a replacement is named, existing contracts remain understandable, and removal becomes a later governance decision.

Governance operating model

Change communication

Version the impact. Deprecate the contract before removing it

Concord synchronizes one workspace version across owned packages and preserves deprecated compatibility APIs. Release policy must remain equally explicit about what the repository provides—and what it does not.

A version number is useful only when consumers can connect it to contract impact. Deprecation creates a compatibility period: a replacement is named, the old path remains understandable, migration guidance is available, and removal becomes a later decision.

Concord currently synchronizes one repository version across owned packages. It does not yet encode changelog generation, release cadence, Git tagging, Changesets, or semantic-version enforcement as repository automation.

Release identity 1.0.0 Root package.json is the current workspace version source.
Synchronization scope 10 owned package manifests Root, @dsl/*, and @concord/* packages share the same version.
Compatibility evidence Deprecated APIs remain usable during migration Source keeps old contracts while naming their replacements.

Repository version contract

One root version governs the owned workspace

The repository implements two explicit commands: one synchronizes owned package versions to the root package, and one fails when an owned package drifts.

01 · Canonical source Root package.json "version": "1.0.0"
→
02 · Write path pnpm sync:version Updates owned workspace package manifests to the root version.
→
03 · Synchronized surface 10 owned package.json files concord-design-system, @dsl/*, and @concord/*.
Drift is testable.

pnpm check:version compares every owned package manifest with the root version and exits with an error when a mismatch exists.

Release boundary

Version synchronization is not release automation

The repository proves version parity. It does not currently prove a complete publication or semantic-versioning workflow.

That distinction matters in enterprise documentation. A synchronized 1.0.0 workspace does not by itself tell consumers whether a change is major, minor, patch, when a release ships, or where a changelog entry will be generated.

Change impact

Classify the contract change before choosing release mechanics

Concord can govern change impact without pretending the repository already enforces a major/minor/patch mapping.

01 · Additive Existing consumer contracts remain valid New tokens, states, variants, documentation, or capabilities that do not invalidate current use.
02 · Corrective Implementation moves back toward the documented contract Bug, accessibility, resilience, or consistency corrections still require regression evidence.
03 · Contract change An existing consumer assumption no longer holds Markup, API, behavior, tokens, delivery, or documented expectations may require migration.
04 · Deprecation / removal Compatibility is intentionally transitional Replacement, migration guidance, support window, and eventual removal decision become explicit.
Impact first; number second.

If Concord later adopts an automated SemVer policy, that policy can map these decisions to release numbers. The current repository does not yet make that mapping.

Public contracts

Breaking change is broader than a JavaScript signature

Consumer contracts cross the full design-system surface.

A release review should ask whether consumers must change markup, tokens, CSS, custom-element APIs, framework adapters, accessible interaction, or documented behavior. A change can be breaking even when TypeScript still compiles.

01 Semantic markup HTML structure · native semantics · documented composition
02 CSS & tokens Custom properties · token names · state and theme contracts
03 Lit API Attributes · properties · events · custom-element behavior
04 Framework adapters Typed props and event adapters over the shared element
05 Accessible behavior Keyboard · focus · names · state announcements
06 Documentation Supported usage · constraints · migration guidance

Deprecation path

Deprecation is a compatibility period, not a comment

The source annotation matters because it names the replacement, but sustainable deprecation also preserves a usable path while consumers migrate.

  1. 01
    Choose the replacement Resolve ownership and the preferred contract first.
  2. 02
    Mark the old contract @deprecated names what consumers should use instead.
  3. 03
    Preserve compatibility Old and new contracts coexist where migration time is needed.
  4. 04
    Guide migration Docs explain the replacement, behavior differences, and adoption path.
  5. 05
    Decide removal separately Removal follows evidence and consumer impact—not annotation age.

Source evidence

Current compatibility code shows three migration patterns

Current source preserves deprecated public contracts that exercise these compatibility patterns.

The patterns differ because compatibility is contextual. Some aliases still participate in behavior, one property falls back to a newer accessibility contract, and one token-engine option remains accepted as an intentional no-op.

Slider · Boolean aliases markers → tickMarks Runtime behavior accepts either value: the new contract and deprecated alias coexist. Compatibility pattern · functional alias
Slider · Boolean aliases markerLabels → rangeLabels Range-label behavior remains available through the deprecated attribute during migration. Compatibility pattern · functional alias
Stepper · Accessible naming label → accessibleLabel The newer explicit accessible-label contract wins; the old label remains a fallback. Compatibility pattern · fallback alias
Token engine · Architecture policy skippedTiers remains accepted The option is deliberately retained as a no-op for existing token-engine consumers. Compatibility pattern · accepted no-op

Removal gate

A deprecated contract is not automatically ready to delete

Removal should be a reviewable governance decision with consumer evidence and release communication.

ReplacementIs the preferred contract stable and documented?
MigrationCan consumers move without inventing a local substitute?
AdoptionDo known consumers still depend on the deprecated path?
ImpactWhat markup, API, token, behavior, or accessibility contract changes?
CommunicationHow will the breaking removal be made visible?
ValidationWhat tests prove the replacement and removal path?

Repository evidence

Do not imply release machinery the repository does not provide

Version governance is strongest when supported capabilities and absent automation are equally explicit.

Concord demonstrates synchronized package identity and compatibility-preserving deprecations. The current repository does not provide an automated changelog, Changesets, semantic-release, or a repository-enforced publish cadence; local Git-tag evidence is reported separately below.
