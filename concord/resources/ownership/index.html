Resources / Governance

Ownership

Ownership keeps shared contracts coherent by placing each responsibility in one canonical layer. Contributions may be distributed; the source of truth and responsibility boundary should remain explicit.

Governance operating model

Ownership thesis

One canonical owner per responsibility. Many contributors.

In Concord, ownership means the layer or canonical source responsible for a contract—not a claim that one person authors every change.

Contributors can propose, implement, review, test, and document changes across the system. Coherence comes from keeping each decision in the source or layer that actually owns the responsibility.

The repository encodes architectural ownership extensively, but it does not currently encode named human maintainers, CODEOWNERS routing, mandatory approver roles, or an escalation hierarchy.

Contribution Open input Needs and evidence may originate with any consumer or delivery layer.
Canonical ownership Responsibility lives in one authoritative layer Change the contract where its semantics, styling, behavior, or policy actually belong.
Consumption Many downstream interfaces Adapters, docs, generated artifacts, and products consume without redefining upstream truth.

Repository boundary

Architectural ownership is encoded. Human assignment is not.

Concord can prove where responsibilities belong without inventing an organizational chart.

Durable repository rules describe source-of-truth boundaries, dependency direction, adapter responsibilities, documentation ownership, and validation. Human accountability can sit above that architecture, but the current repository does not name teams or people as mandatory owners.

Repository encodes
Canonical source boundariesRaw HTML, tokens, CSS, adapters, and documentation each have explicit responsibility.
Dependency directionUpstream and downstream ownership is constrained by architecture rules and validation.
Change evidenceTests and validation prove contracts rather than relying on reviewer intuition alone.
Repository does not currently assign
CODEOWNERS routingNo CODEOWNERS file is present.
Manifest-level human owners0 of 31 component manifests expose owner-like top-level fields.
Root package maintainersNo author, contributors, or maintainers metadata is present.
Do not confuse missing assignment automation with missing architecture.

Concord has strong responsibility boundaries today. Team names, approver matrices, SLAs, and escalation paths should be added only when an organization deliberately adopts them.

Single-owner rule

One responsibility should not have competing sources of truth

The repository repeatedly uses single-owner rules to keep implementation, documentation, and delivery views aligned.

Canonical HTML is authored once. Documentation selects it rather than copying it. Lit and React represent the same contract rather than becoming alternate component systems. Token references move toward the appropriate upstream owner instead of duplicating shared meaning downstream.

01 · Canonical owner Decision is authored in the layer that owns it One implementation source carries the authoritative contract.
→
02 · Derived / adapter views Interfaces consume the canonical contract Documentation, Lit, React, generated artifacts, and examples stay downstream.
→
03 · Consumers Products integrate without forking ownership Product-local state and workflow remain application-owned.
Duplication is an ownership smell.

Two independently authored sources for the same responsibility create drift even when their current output happens to match.

Contribution vs ownership

Authorship does not transfer decision rights

The person or layer implementing a change is not automatically the owner of the contract being changed.

Contributor Brings need, evidence, implementation, or review Contribution is intentionally distributed.
Ownership question Which layer is responsible for this decision? Canonical placement is resolved before convenience determines architecture.
Owner boundary Accept, redirect, or keep the change product-local A valid outcome does not always change the shared system.

Responsibility routing

Move a decision upstream only when the responsibility is shared

Escalation is architectural before it is organizational: first determine where the decision belongs.

Consuming application Permissions, record truth, business rules, and product orchestration remain product-owned.
Component semantics or behavior →

Review model

Review follows the affected contract, not a fixed approver matrix

The relevant perspectives change with the contract being modified.

Concord already treats design, engineering, accessibility, product/consumer needs, and documentation as meaningful inputs to shared-system decisions. The repository does not, however, encode those perspectives as mandatory named roles or required approvals.

Design Intent, reusable meaning, visual/system coherence
Engineering Canonical source, API shape, dependency direction, runtime behavior
Accessibility Semantic meaning, keyboard/focus behavior, state communication
Product / consumers Real use cases, migration cost, adoption evidence, product-local constraints
Documentation Supported usage, source truth, change communication, migration guidance
Perspective ≠ mandatory role.

Review should cover the affected contract. Do not infer an organizational approval chain from the architectural concerns that need evidence.

Enforcement boundary

Repository evidence makes ownership durable

Concord relies on durable architecture rules and executable checks rather than undocumented convention.

AGENTS.md defines source-of-truth discipline, token ownership, component composition, adapter boundaries, documentation truthfulness, and validation expectations. Focused tests then protect canonical-source, dependency, contract, and responsive behavior.

Durable rules AGENTS.md Defines architectural ownership and responsibility boundaries.
Canonical-source evidence Source / manifest / documentation contracts Tests prevent independently authored substitutes from becoming alternate truth.
Architecture validation Dependency and token checks Mechanically rejects invalid direction, missing references, and structural contract failures.
Repository validation pnpm validate + focused suites Changed responsibilities must be proven at the narrowest useful boundary.
Architectural ownership Explicit and repository-backed
Human assignment automation Not currently encoded
Operating implication Add organizational routing without changing canonical technical ownership

Stewardship loop

Ownership is continuous maintenance of a shared contract

Stewardship keeps responsibility coherent before, during, and after a contribution lands.

01
Clarify Define the responsibility boundary Know what belongs here and what stays outside.
02
Coordinate Bring the relevant perspectives together Design, engineering, accessibility, consumers, and docs contribute evidence as needed.
03
Prove Validate the changed contract Use source checks, tests, accessibility, resilience, and generated evidence.
04
Communicate Make impact and migration visible Docs, lifecycle status, and versioning explain the consumer-facing decision.
05
Revisit Use adoption feedback to refine the system Repeated friction can reveal a misplaced responsibility boundary.
Adoption feedback can reopen Clarify ↑ ↓

Ownership record

Make responsibility legible before the next change arrives

Even without named-team automation, a system decision should leave enough context for future contributors to find the right boundary.
