Resources / Architecture

Token Architecture

Concord treats tokens as a validated ownership graph rather than a flat value catalog. One canonical graph preserves authored relationships for the web, resolves platform-ready values for Swift and Kotlin, and constrains theme and density overrides without creating parallel token systems.

Architecture thesis

Design decisions become governed system contracts

A token is a named design decision with an owner, a place in the reference graph, and a predictable path into generated artifacts.

The architecture separates **where a decision originates** from **how a destination platform serializes it**. CSS, Swift, and Kotlin are outputs of the graph, not independent sources of truth.

01 · Foundation Reusable values Raw primitives and low-level design decisions
→
02 · System Shared contracts Stable roles reused across experiences
→
03 · Semantic Purpose & context Meaning assigned to system decisions
→
04 · Component Local contract Decisions that genuinely belong to a component
Ownership rule Reference upstream. Never make upstream ownership depend on downstream implementation.

Direct references to the most appropriate upstream contract are valid; artificial pass-through aliases are not required.

Source boundary

Design tools can feed Concord; they do not become the contract

Canonical token JSON is the governed handoff where Concord’s validation, ownership, and generation rules begin.

Upstream design tooling may author, export, or help maintain those decisions, but the design-tool representation is not the runtime source of truth.

For example, a Figma workflow using Tokens Studio or another structured token export can sit upstream of Concord. That handoff must be normalized to Concord’s canonical token model before the normal validation and generation pipeline applies.

Optional upstream authoring Design tools & structured exports Examples: Figma, Tokens Studio, or another token-producing workflow
→
Normalization boundary Map into Concord’s canonical model Import automation is an integration concern, not part of token ownership
→
Governed source Canonical token JSON Validation, references, overrides, and emitters start here
Do not imply live Figma synchronization unless the repository proves it.

The architecture supports design-tool inputs as an upstream source boundary; it does not make a design tool, plugin, or export format a required Concord dependency.

Tier ownership

Each tier answers a different design question

The four tiers separate raw vocabulary, shared system roles, contextual meaning, and component-owned decisions.

Foundation What values exist?

Primitive color, spacing, type, radius, elevation, motion, and other reusable decisions.

Can be referenced by downstream ownership.
System What does the shared system standardize?

Stable cross-experience contracts that should not be reinvented by every semantic or component role.

May reference Foundation.
Semantic What purpose does the decision serve?

Contextual meaning such as action, surface, content, feedback, or other purpose-oriented roles.

May reference the appropriate upstream contract.
Component What belongs specifically to this component?

Only decisions whose ownership is genuinely local to a component API or visual contract.

May reference Foundation, System, or Semantic when appropriate.

Reference contract

The graph is directional, not ceremonial

References move toward appropriate upstream ownership; validation rejects dependencies that reverse that direction.

The goal is not maximum indirection. The goal is explicit ownership and predictable change propagation.

Valid direction
Component→ Semantic→ System→ Foundation

Ownership can depend on an appropriate upstream contract.

Rejected direction
Foundation must not reference Semantic / Component

Upstream ownership cannot depend on downstream implementation.

Direct reference
Component→ System

No pass-through Semantic alias is required when System is the correct owner.

01Duplicate keysRejected before generation
02Source validityValidated at the canonical source
03Reference directionUpward ownership violations are errors
04ResolutionFlattened from the validated graph

Build pipeline

Validate once before any platform emitter runs

Canonical token JSON is validated and prepared once, then the same graph feeds sibling Web, iOS, and Android emitters.

  1. 01Canonical JSONAuthored token source
  2. 02Parse & validateKeys, source, ownership
  3. 03Flatten & resolveValidated reference graph
  4. 04Prepare viewsAuthored + resolved + provenance
  5. 05Emit artifactsWeb · iOS · Android
Generated artifacts are downstream.

CSS, Swift, and Kotlin output are consequences of the graph. They never become a second source of design decisions.

Graph representations

One decision graph, two useful views

The web and native targets need different representations of the same decision graph.

**Authored/reference-bearing view**

CSS should preserve intentional token relationships so runtime custom properties can continue to express `var(...)` references where the graph intends inheritance or rebinding.

**Resolved view**

Swift and Kotlin consume build-time resolved values appropriate to generated native token packages.

Both views come from the same prepared graph. Platform output may change syntax, naming, namespaces, types, serialization, and file organization without introducing new design decisions.

Authored / reference-bearing Preserve intentional relationships

Used by the web emitter so CSS custom properties can retain meaningful var(...) references and runtime rebinding.

Relationship component → semantic → system
Resolved Provide platform-ready values

Used by native emitters where generated Swift and Kotlin packages need build-time resolved token values.

Override governance

Themes and density rebind the graph; they do not fork it

Themes and densities are override sources applied to the same graph, not separate token architectures.

Each override source is validated and restricted to configured allowed tiers. Theme and density remain independent dimensions so a visual language can vary without coupling it to compactness.

Combined theme/density CSS is generated from those validated sources. The dedicated Theming & Density page owns the deeper consumption model.

Theme What visual language is this?

Validated override sources may change only the tiers their configuration permits.

Density How compact or spacious is it?

Density remains an independent override dimension rather than being baked into each theme.

Combined output Validated sources compose

The build generates combined theme/density CSS from the same canonical ownership graph.

No parallel token trees.

A theme or density source can rebind approved ownership; it does not become another canonical design system.

Platform distribution

Emitters translate representation, not intent

Web, iOS, and Android are sibling outputs of the same prepared graph, not separate token systems.

Native generation must remain removable infrastructure. Removing a native target must not change canonical token JSON, CSS variable naming, CSS serialization, theme/density behavior, or the public web runtime contract.

Generated Swift and Kotlin tokens distribute design decisions; they do not imply native iOS or Android component libraries.

Shared source Platform-neutral prepared graph One validated set of design decisions
Web emitter CSS Names · custom-property syntax · reference serialization
iOS emitter Swift Native naming · types · namespaces · file organization
Android emitter Kotlin / Compose Native naming · types · namespaces · file organization

Reproducibility

Generated output is evidence, not authoring state

The token build includes a check mode that compares expected generated token files with committed/generated output and reports missing or stale artifacts.

Do not edit generated CSS or native token output as an independent source. Fix the canonical graph, validation rule, configuration, or emitter that owns the decision.

Source Canonical token graph Change the decision here
→
Build Generate expected artifacts Apply validation and emitter rules
→
Check mode Compare expected vs committed Report missing or stale generated output
Fix the owner, not the artifact.

When generated output is wrong, change the graph, validation rule, configuration, or emitter responsible for it.

Change review

Review the decision before reviewing the diff

Review ownership, dependency direction, override authority, platform outputs, and consumer impact before treating a token diff as accepted.

  1. 01OwnershipIs this the correct tier?
  2. 02ReferencesDoes dependency direction remain valid?
  3. 03OverridesCan theme or density own this change?
  4. 04PlatformsWhat changes in CSS, Swift, and Kotlin?
  5. 05GenerationAre committed artifacts current?
  6. 06ConsumersWhat contract boundary is affected?

This is a review model, not a claim that every step is automated.
