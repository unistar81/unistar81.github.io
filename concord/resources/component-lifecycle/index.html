Resources / Governance

Component Lifecycle

A component has responsibilities beyond its first implementation. Lifecycle status communicates contract maturity and consumer risk while evidence determines whether the adoption posture should change.

Governance operating model

Lifecycle contract

Status communicates consumer risk, not component age

Concord encodes four component-status values in the manifest contract. Lifecycle governance explains what those values mean for adoption and what evidence should justify a transition.

A component can be technically complete and still be immature as a shared contract. Status should therefore describe the confidence consumers can place in semantics, API stability, accessibility, resilience, delivery behavior, and migration expectations.

Repository evidence and governance intent stay separate: the schema defines the statuses the system can encode today; the operating model defines how teams should decide when to change them.

Machine-readable source Component manifest status is required by the current schema.
Maturity evidence Contract + quality proof Tests, accessibility, resilience, delivery, documentation, consumer evidence.
Consumer meaning Adoption posture Status tells consumers how much change and migration risk to expect.

Encoded status contract

Four values are repository truth

The current TypeScript contract and JSON Schema agree on the same closed set: experimental, beta, stable, and deprecated.

  1. 01
    Experimental Change expected

    An implementation exists, but the shared contract is still being validated and may change as evidence accumulates.

  2. 02
    Beta Controlled adoption

    The component is usable while semantics, API stability, delivery behavior, and consumer evidence continue to mature.

  3. 03
    Stable Normal adoption

    The supported contract is mature enough for normal adoption; breaking change now requires explicit lifecycle handling.

  4. 04
    Deprecated Migration

    Existing consumers receive a transition path while new adoption stops and a replacement or migration direction is communicated.

Status vocabulary is a contract.

The manifest schema rejects status values outside this set. Governance should not invent a fifth encoded state without first changing the machine-readable contract.

Governance boundaries

Lifecycle begins before status and can continue after it

Intake and eventual removal are real lifecycle decisions, but they are not current manifest status values.

This resolves a mismatch in the earlier documentation proposal: Proposed and Retired are useful process concepts, but the current repository cannot encode them as component status.

Keep those edges visible as governance boundaries rather than silently expanding the enum in documentation.

Before encoded status Contribution intake Problem · ownership · contract · evidence plan Governance step · not a manifest status
→
Encoded lifecycle Experimental → Beta → Stable → Deprecated The manifest carries one of these four values.
→
After deprecation Removal / retirement Migration complete · support decision · removal coordinated Governance outcome · not a manifest status

Repository snapshot

Status evidence comes from authored manifests

This page reads the authored component-manifest inventory when the documentation is built. The snapshot is evidence of that build, not a durable maturity rule.

beta 0 None in current inventory

deprecated 0 None in current inventory
Inventory is not the maturity model.

A status count describes the current repository. Promotion still requires evidence for each component rather than a schedule or target percentage. Stable is the normal public documentation posture, so component headers do not repeat a Stable badge. Experimental, beta, and deprecated remain explicit exception states.

Version signals

Lifecycle status is not the same thing as version

Concord currently exposes three different signals that answer three different questions.

Confusing maturity with schema or package version makes lifecycle decisions ambiguous. Component status describes adoption confidence; manifest schema version describes metadata shape; repository/package version identifies the codebase release line.

Component maturity status: stable Can consumers rely on this contract?
Manifest format schemaVersion: 1.0.0 Which metadata shape is being validated?
Repository / package version: 1.0.0 Which codebase release identity is this?

Transition gates

Movement requires evidence, not elapsed time

Lifecycle transitions should happen because the contract’s risk profile changed—not because a component has existed for a certain number of sprints.

Experimental → Beta Prove a coherent shared contract exists
  • Canonical semantics and component ownership are explicit.
  • Manifest metadata, variants, states, accessibility, and dependencies are valid.
  • Baseline implementation, documentation, and tests exist for the claimed contract.
Beta → Stable Prove normal adoption is a responsible recommendation
  • Semantics, API, behavior, and visual contracts have survived meaningful use.
  • Accessibility, content resilience, theme/density, and responsive behavior are evidenced.
  • Delivery interfaces remain aligned and known consumer feedback has been incorporated.
Stable → Deprecated Prove the system has a better direction
  • Document why new adoption should stop.
  • Name the replacement or migration direction where one exists.
  • Coordinate consumer communication with versioning and deprecation policy.
Deprecated → Removal Treat removal as a separate governance decision
  • Removal is not a fifth manifest status in the current repository.
  • Migration impact must be understood before support ends.
  • Release mechanics belong to Versioning & Deprecation, not this status enum.

Maturity evidence

A component matures across several contracts at once

Stable should mean more than “the CSS looks finished.”

Concord’s architecture spreads responsibility across semantics, authored CSS, tokens, behavior, accessibility, content handling, manifests, and optional delivery adapters. Lifecycle evidence needs to reflect that system rather than one implementation layer.

01Semantic contractHost choice · naming · relationships · native behavior
02API & behaviorAttributes · events · states · owned interaction
03AccessibilityKeyboard · focus · names · states · assistive technology
04Visual resilienceTheme · density · responsive behavior · content pressure
05Delivery integrityHTML/CSS · Lit · framework adapters where applicable
06Consumer evidenceReal adoption · feedback · documentation clarity · migration risk

Status propagation

Encode status once; preserve it downstream

The authored component manifest is validated before catalog generation. The generated catalog clones the manifest contract, and distribution transforms preserve that status field.

01 · Canonical metadata Authored component manifest "status": "stable"
02 · Validation Schema + semantic checks Closed enum · required field · contract validation
03 · Catalog Validated component catalog Component manifests are cloned into catalog output.
04 · Distribution Transformed catalog Status remains part of the component manifest contract.
Documentation synchronization is still a responsibility.

The collected repository proves manifest and catalog status propagation. It does not prove that every documentation status surface is automatically generated from component manifests.

Lifecycle feedback

Maturity is continuously re-evaluated

Enterprise design-system practice treats testing, feedback, documentation, and iteration as lifecycle inputs rather than work that ends at launch.

This carries forward a useful principle from the earlier DLS reference: automated and visual testing, accessibility checks, consumer feedback, cross-functional collaboration, documentation, training, versioning, and iterative design all contribute to sustainable component quality.

Concord uses that material as architectural precedent, not as proof that every enterprise process is automated in this repository.

01 · ProveTesting & accessibilityCatch regressions and contract failures.
02 · ObserveConsumer use & feedbackFind friction that isolated implementation work cannot reveal.
03 · ExplainDocumentation & trainingMake adoption expectations and constraints legible.
04 · RefineDesign & engineering iterationFeed evidence back into the shared contract.

Status decision

Change lifecycle status only when the consumer contract changed

A status transition should leave a reviewable reason, evidence, and consumer guidance—not just a changed string in JSON.

EvidenceWhat proves the new posture?
ConsumersWho can adopt, continue, or must migrate?
Contract impactWhat semantics, API, behavior, or delivery changed?
GuidanceWhat must documentation communicate now?
Deprecation onlyWhat replacement and migration direction exists?
Lifecycle is governance; versioning is release communication.
