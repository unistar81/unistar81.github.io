Contribution Model

Concord treats contribution as a system decision, not simply a code submission. A useful contribution starts with a recurring need, identifies the contract that should own the decision, brings the evidence needed to evaluate system impact, and changes canonical sources only when the shared system should actually change.

Governance operating model

Governance thesis

One shared system. Many contributors. One canonical decision path.

One shared system. Many contributors. One canonical decision path.

Contributions should reduce parallel local solutions rather than create them. The goal is not to make every product need part of Concord; the goal is to decide deliberately which needs belong in the shared language and which remain application concerns.

The current repository already encodes durable architecture rules in AGENTS.md, canonical source-of-truth boundaries, machine-readable manifests, synchronized contract expectations, and validation commands. The broader contribution sequence on this page is an operating model: it describes how those rules should be applied to system change without claiming organizational approvals or automation the repository does not contain.

Contribution starts local Need · evidence · proposed ownership Anyone working with the system can surface a reusable problem.
→
Canonical system decision Accept · redirect · reuse · request evidence · defer The shared contract changes only when the responsibility belongs upstream.
→
Consumer outcome Shared adoption or product-local ownership A valid governance result does not always produce a new system feature.

Operating model

Separate contribution mechanics from decision rights

Contribution mechanics answer how a change moves. Decision rights answer where authority stays.

A contributor can surface a need, gather examples, propose the owning layer, and implement a candidate change.

The shared system owns canonical design decisions, semantic component contracts, public token/API boundaries, documentation truth, and the evidence required to keep delivery layers synchronized.

Consuming products retain application routing, data, business logic, workflow composition, product-specific state, and adoption decisions that do not belong in a reusable component contract.

No portfolio-only team names, councils, or approval roles are assumed.

Contribution path

Move from a local need to a system decision

Seven steps move a reusable need from intake to a published system decision.

  1. Phase 01 · Frame Establish the system case
    01 · Need Identify the system need Recurring problem · affected consumers · current gap
    02 · Ownership Choose the owning layer Foundation · token · component · layout · pattern · template · docs
  2. Phase 02 · Define Make the contract explicit
    03 · Contract Define what must stay stable Semantics · accessibility · tokens · behavior · public API
  3. Phase 03 · Change Change source and prove it
    04 · Source Implement upstream Change canonical source, never generated evidence
    05 · Evidence Prove the changed contract Tests · manifests · adapters · docs · generated checks
  4. Phase 04 · Decide Evaluate impact and record the decision
    06 · Impact Review the blast radius Themes · density · accessibility · resilience · consumers
    07 · Decision Publish the decision clearly Decision · rationale · status · migration guidance when needed
A contribution may stop before implementation.

A product-local need, duplicate contract, or misplaced responsibility is a valid governance outcome.

Intake

Start with the problem, not the requested API

A useful contribution brief establishes the need, affected consumers, current contract gap, and why Concord should own the responsibility before a solution is proposed.

01 Recurring need What problem appears across more than one use case?
02 Affected consumers Who experiences it and under what conditions?
03 Existing contract gap What current component, pattern, token, or layout rule was evaluated?
04 Why shared Why should Concord own this instead of the application?
Weak request "Add a compact dashboard card variant."
→
System question "Which reusable contract is missing, and does Card actually own it?"

Contract definition

Define the contract before writing the convenience layer

Before implementation, define what must remain stable.

For component work, start with semantic HTML and accessibility responsibilities. Decide whether native HTML already owns the required behavior and whether the proposed host is justified by the component's meaning rather than naming consistency.

For tokens, preserve tier ownership and shared intent. Do not create a component-level token for a decision that belongs upstream.

For behavior, prefer native browser behavior and add JavaScript only where the contract requires it.

For delivery layers, keep Lit, React, Storybook, generated distributions, and documentation downstream of the canonical contract.

Semantics Native meaning first Choose native elements where the platform already owns the contract.
Accessibility User requirements belong in the contract Naming · focus · relationships · state · keyboard behavior
Design decisions Keep ownership upstream Reuse system/semantic intent before adding component-specific decisions.
Behavior Browser first Add JavaScript only where native behavior does not satisfy the component.
Delivery Adapters consume Lit, React, Storybook, and docs remain downstream interfaces.

Collaboration model

Bring the right feedback in before the contract is frozen

Governance should bring feedback forward, not reserve it for a final gate.

Design contributes visual intent and interaction expectations. Engineering protects semantics, architecture, API boundaries, deterministic output, and implementation quality. Accessibility evaluates user-facing requirements early enough to influence the contract. Product and consuming teams provide realistic use cases, adoption feedback, and evidence that a need is actually shared. System stewardship keeps those inputs coherent with the canonical architecture.

This model does not require every discipline to approve every edit. It requires the right concerns to enter before the contract is frozen.

EngineeringArchitecture & behaviorSemantics · API · deterministic output · implementation
AccessibilityUser-facing requirementsNames · focus · keyboard · state · assistive technology
Product / consumersReal use casesAdoption pressure · composition · product constraints
Shared review loop Contribute → surface concerns early → refine the contract → re-evaluate evidence Feedback enters while the contract is still inexpensive to change.
System stewardship Hold canonical coherence Ownership · evidence · cross-layer consistency · decision clarity

Enterprise precedent

Keep the core coherent without closing the contribution path

Prior enterprise DLS work reinforces three durable governance lessons.

First, a shared core remains maintainable when local teams can surface needs and extensions without silently forking the core language.

Second, regular collaboration and feedback during component development is more effective than design, engineering, and accessibility reviewing one another only after implementation is complete.

Third, documentation and feedback loops are part of adoption and governance, not downstream polish.

Concord carries forward those architectural lessons while deliberately avoiding organization-specific machinery such as a governance council, business-unit approval structure, or enterprise CI/release policy that this portfolio repository does not implement.

Shared core Canonical standards stay centrally coherent Brand/system rules, accessibility, reusable contracts, and documentation remain common.
Distributed input Local needs can surface without forking the language Contribution channels preserve adaptability without turning every exception into a new core rule.
Continuous feedback Review while the component is being shaped Design, engineering, accessibility, and consumers influence the contract before completion.

Repository enforcement boundary

Separate encoded rules from operating-model intent

The current repository proves several governance mechanisms.

The collected repository snapshot does not contain CODEOWNERS, a contribution guide, pull-request or issue templates, GitHub workflow files, an RFC/ADR system, changesets, a changelog mechanism, or repository evidence of mandatory named-role approvals.

Therefore this page documents Concord's contribution operating model and architecture expectations. It does not claim that every stage is automatically enforced before merge or release.

Decision outcomes

A good review can produce more than one correct answer

Acceptance is only one valid result; a clear redirect, reuse decision, request for evidence, product-local outcome, or deferral can also be correct.

01 · SharedAdopt into the shared contractReusable · architecture-aligned · sufficiently evidenced
02 · LocalKeep product-localApplication composition · workflow · business logic · data
03 · ReuseReuse the existing systemThe underlying need is already supported
04 · HoldRequest more evidenceImpact, accessibility, or consumer need is not yet clear
05 · DeclineDefer or rejectDuplicates truth · weakens semantics · creates framework ownership · one-off exception
Make the reason as clear as the implementation.

Governance is successful when the reason for the decision is as clear as the implementation.
