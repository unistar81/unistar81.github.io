Using React

React is Concord’s current typed framework adapter. It gives React applications idiomatic component APIs while preserving the same Lit Web Components, semantic HTML, external CSS, tokens, accessibility, and component-owned behavior used by the other delivery paths.

Framework adapter

Runtime ownership and compatibility

The consuming application owns React and React DOM. @dsl/react declares both as peers with range ^18.3.1 || ^19.0.0; install matching React/React DOM versions and matching React type majors. Clean packed-consumer checks exercise React 18.3.1, 19.0.0, 19.2.8, and 19.3.0, including TypeScript declarations and the rich-content portal bridge. This is client-rendered delivery qualification, not an SSR or hydration claim.

Registration

React entries register their required Lit elements

React adapters consume the shared Lit delivery implementations of the canonical HTML/CSS contract.

The aggregate adapter entry imports ./register.js. That module calls registerConcordElements(), which registers the complete Concord Lit inventory when a browser CustomElementRegistry is available. The function is guarded so repeated calls do not register the elements again, and it returns without browser globals during non-browser evaluation. Selective entries such as @dsl/react/button register only that component and its required dependencies.

Registration is infrastructure for the adapter layer; it does not make React the owner of the component implementation.

Idempotence applies to one installed/bundled Concord copy in a document. Deduplicate that copy across application bundles. A foreign or independently bundled definition using the same tag fails explicitly and retains the existing constructor. The React adapters use fixed default tags; they do not implement multi-version isolation or automatic custom-tag remapping. Lit retains explicit defineDsl* registration, including an optional tag name, with matching CSS/HTML namespace decisions owned separately.

API boundary

Props adapt the shared contract; they do not redefine it

React props should make the existing component contract ergonomic in JSX rather than create a parallel API.

For Button, current React usage includes component-owned properties such as label, variant, size, leadingIcon, trailingIcon, accessibleLabel, shape, and disabled.

The adapter must not reimplement markup, styling, token logic, accessibility behavior, or component state already provided by the shared component contract and its Lit delivery implementation.

Localized component actions accept complete labels: Input showPasswordLabel / hidePasswordLabel, Alert dismissLabel, Modal/Popover closeLabel, Tabs mobileSelectLabel, and Stepper decreaseLabel / increaseLabel. Existing label, item, trigger, content, and action props still carry product copy. Empty new properties preserve the previous English defaults. The application owns translations and must update a Stepper action label if its increment or subject changes; Concord adds no locale provider or translation catalog.

State ownership

Application state stays with the application

React application state belongs to the consuming application unless the component contract explicitly owns that state.

Use React state to coordinate product data, routing, application composition, and application-level workflows. Let Concord components continue to own the interaction state and browser behavior defined by their component contracts.

A framework adapter should translate events and properties across the boundary, not move application concerns into the design system or move component responsibilities into every consuming application.

Events & typing

Map events into React without inventing a second event model

`@lit/react` provides the adapter bridge between custom-element APIs and React.

Concord maps standard form events to React callbacks where appropriate and gives custom Concord events explicit typed callback names. Event detail types come from the shared Lit package so React does not invent a second event contract.

TypeScript typing is part of the React delivery value: consumers receive component property and event contracts through the adapter instead of manually coercing custom-element values.

System concerns

React inherits the design system; it does not restyle it

React does not own Concord styling.

The rendered elements consume the same external component CSS and generated CSS custom properties as HTML/CSS and Lit delivery. Theme, appearance, and density remain system-level token concerns inherited by the rendered component tree.

Do not create React-only token values, theme state, CSS-in-JS copies of component styles, or framework-specific visual implementations.

Current adapter surface

One adapter package across the component system

The current public React entry point exports adapters across actions, forms, navigation, content, feedback, and overlays, including Button, Input, Card, Modal, Tabs, Accordion, Menu, Tooltip, and other supported Concord components.

Treat the current package export map and `packages/react/src/index.ts` as the source of truth for the exact adapter inventory. Do not maintain a duplicate hard-coded inventory in durable documentation.

Architecture proof

React applications receive typed framework ergonomics without paying for a second design-system implementation. Concord can evolve its semantic, CSS, token, accessibility, and component behavior contracts once while React remains a delivery adapter over those shared decisions.
