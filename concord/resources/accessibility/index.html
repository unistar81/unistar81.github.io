Resources / Quality

Accessibility

Concord treats accessibility as a shared system contract that must survive theme changes, responsive composition, component enhancement, and delivery technology. This page connects the foundation principles to repository-proven semantics, interaction behavior, visual environments, resilience checks, and ownership boundaries.

Quality thesis

A shared contract, not a final audit

Accessibility is not a final audit step.

Concord owns reusable component semantics, interaction contracts, focus treatments, token-driven visual states, framework-neutral behavior, and regression evidence where those concerns belong to the design system.

Consuming products still own application context, page structure, workflow order, meaningful content, feature-specific validation, and the complete accessibility of the assembled experience.

The boundary matters: a design system can make accessible composition easier and enforce stable component contracts, but it cannot certify an unknown product merely because the components are accessible in isolation.

Ownership boundary

Keep ownership explicit

The consuming application remains responsible for context the component cannot know.

Examples include:

Concord owns Component semantics and reusable interaction
  • native host choice
  • component-owned ARIA relationships
  • keyboard behavior for composite patterns
  • shared focus and state treatment
  • forced-colors and contrast preference handling
  • component regression contracts
Consuming product owns Meaning in the assembled application
  • page structure and heading hierarchy
  • feature labels, instructions, and errors
  • workflow and cross-component focus order
  • routing and destination meaning
  • domain-specific announcements and recovery
  • end-to-end product review with real content
Boundary rule Do not push product business logic into components merely to centralize accessibility work.

Semantic baseline

Native semantics are the baseline

Use native elements when the platform already owns the semantic and interaction model.

Repository contracts use native buttons, inputs, checkboxes, selects, ranges, and dialogs. Native controls retain browser activation, focusability, form behavior, disabled state, and other built-in semantics before Concord styling is applied.

ARIA supports relationships and composite patterns where needed. It should not replace native HTML merely for visual or framework consistency.

Focus & state

Focus and state survive theme changes

Focus is a shared design-system contract.

Concord exposes semantic focus outline decisions for width, offset, style, and color. Component styles consume those contracts through :focus-visible or the appropriate composite focus boundary.

State must remain available through semantics or structure as well as color. Repository contracts use native disabled state and pattern-specific state such as aria-selected, aria-expanded, aria-current, aria-invalid, and related relationships where the component model requires them.

Themes may change visual expression, but they must not make focus or state disappear.

Accessibility environments

User preferences sit outside the brand matrix

Accessibility preferences are environmental inputs, not brand themes.

The current repository includes an authored forced-colors: active layer that restores meaningful system colors, boundaries, focus, disabled state, links, fields, menus, modal surfaces, and other essential component distinctions.

The repository also includes prefers-contrast: more adjustments that strengthen shared border, text, and focus roles.

Reduced-motion handling is implemented in animated component styles such as Accordion, Card, and Tabs through the system reduced-duration contract.

These environmental adaptations remain independent from Theme and Density.

User environment Accessibility preferences remain outside Theme and Density

Contrast evidence

Theme freedom increases the amount of evidence required

Theme flexibility increases the amount of accessibility evidence required.

Current automated browser tests use axe-core color-contrast checks against canonical component surfaces and documentation appearance scenarios. Separate Playwright checks exercise dark appearance, forced colors, and increased contrast behavior.

This is repository evidence for the tested surfaces. It is not a claim of universal WCAG conformance for every possible product composition.

01 · Browser rule axe-core color-contrast Canonical component text/surface checks.
02 · Appearance Dark surfaces remain readable Non-default appearance scenarios are exercised.
03 · Environment Forced colors preserves boundaries and focus Playwright emulates the environment where supported.
04 · Preference More contrast strengthens shared roles Border, muted text, and focus roles are checked.
Automated contrast evidence is scoped evidence, not a blanket conformance claim.

The current tests prove the surfaces they exercise. Product compositions still require their own review.

Content & reflow

Content and interaction must survive constrained space

Accessibility includes surviving enlarged text, translation, long labels, unbroken strings, and constrained available width.

Current browser regressions stress system text surfaces and multiple components with long or unbroken content. Tabs also verify their responsive presentation from the component's own available width, including a 320px case.

Detailed stress scenarios belong on the Content Resilience page; the accessibility contract here is that information and interaction must remain available when content or space changes.

Stress inputs Long labels · unbroken strings · translated-length content · narrow containers
Repository examples Button · Pill · Link · Tag · Card · Media · Accordion · Tabs · Slider · Stepper · Tooltip
Responsive evidence Tabs uses its own available width and is exercised at 320px
Detailed stress scenarios continue on Content Resilience.

Here the quality requirement is simple: content expansion or constrained space must not erase information or interaction.

Delivery invariants

One accessibility contract across web delivery

Web delivery technology must not change the accessibility contract.

Static HTML/CSS consumers receive canonical semantic markup and framework-neutral behavior. Lit custom elements preserve or render the same semantic relationships in light DOM. React adapters consume that shared Lit delivery layer rather than inventing another accessibility model.

Native token delivery is different: Swift and Kotlin / Compose output carries shared design decisions, not native component semantics or interaction implementations. Do not infer native component accessibility coverage from token generation alone.

HTML & CSS Canonical semantics Native hosts + framework-neutral behavior
Lit Web Components Same semantic relationships Custom-element delivery preserves the web contract
React adapters Typed ergonomics, same Lit layer No framework-specific accessibility rewrite
Swift / Kotlin tokens Design decisions only No native component accessibility claim

Responsibility model

Evidence boundary

Make strong claims only where evidence is strong

The current repository does not prove universal accessibility conformance for every component, assistive technology, browser, operating system, or consuming product.

Do not turn the presence of ARIA, axe-core, Storybook tooling, or a passing component test into a blanket compliance claim.

The defensible claim is narrower and stronger: Concord treats accessibility as an architectural contract, encodes representative requirements in component manifests, implements and tests concrete semantic and interaction behavior, and carries those web contracts consistently across its current delivery interfaces.

Proven in this repository Representative semantic contracts · keyboard behavior · focus/state styling · contrast checks · preference environments · resilience regressions
Outside the evidence boundary Universal product conformance · every AT/browser/OS combination · accessibility of unknown consuming applications · native component accessibility
