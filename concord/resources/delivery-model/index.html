Delivery Model

Concord delivers one governed design language through different consumption interfaces without making any delivery technology the source of truth. Static HTML/CSS, Lit Web Components, React adapters, and generated native tokens share upstream contracts but carry different runtime responsibilities.

Architecture thesis

One language. Multiple delivery boundaries.

Delivery is a boundary around the system, not a second implementation of the system.

The canonical language remains upstream: token decisions, semantic HTML, authored external CSS, accessibility contracts, component behavior, and layout rules.

Delivery interfaces may add packaging, registration, typed APIs, framework ergonomics, or platform serialization. They must not redefine the design language merely to match the consuming technology.

Shared system contract Tokens · semantic HTML · external CSS · accessibility · behavior · layout Design decisions remain upstream of delivery technology.
Platform-native web Static HTML & CSS Generated distribution · no component framework runtime
Web Component Lit custom elements Optional custom-element delivery over the shared contract
Framework adapter React adapters Typed React ergonomics over shared Lit elements
Platform tokens Swift + Kotlin / Compose Generated token source · not native component libraries
Delivery may translate the interface. It may not redefine the language.

The current repository proves four distinct delivery surfaces:

Static distribution

A complete framework-neutral artifact, not a fallback path

pnpm build:distribution creates the canonical static distribution under dist/vanilla/.

The static distribution is generated from canonical token JSON, semantic HTML, authored external CSS, and framework-neutral behavior modules. Its manifest identifies entry points for token CSS, core CSS, layout CSS, component CSS, examples, and the component catalog.

The resulting artifact does not require React, Lit, Node.js, or runtime token compilation.

pnpm build:distribution:unprefixed produces the verified unprefixed variant. The underlying distribution builder also supports validated prefix transformation rather than requiring consumers to fork source files.

Coexistence boundary

Prefix the distribution when migration needs namespace isolation

The static distribution supports validated namespace transformation at build time. --prefix changes token-variable and component-class prefixes together. --token-prefix and --class-prefix can transform those namespaces independently. --no-prefix removes both prefixes, and build:distribution:unprefixed exposes that verified path directly.

Prefix transformation propagates through generated token variables, public and internal component custom properties, component classes, cascade-layer names, canonical HTML, CSS, and the transformed component catalog.

This capability can support coexistence during migration by reducing naming collisions between Concord and surrounding systems. It does not prove semantic equivalence between systems, choose product composition, define rollout order, or determine when an older local contract can be retired.

Registration boundary

Lit is explicit; React registers its delivery elements

The two package surfaces intentionally have different startup ergonomics while converging on the same custom-element implementations.

Lit package Import is inert

@dsl/components-lit does not register elements on import. Consumers call the relevant defineDsl* function.

sideEffects: false
React package Registration infrastructure is included

The aggregate entry registers all Lit elements when browser globals exist; selective entries register only the component and its required dependencies.

registerConcordElements()
Registration is delivery infrastructure, not component ownership.

Changing registration strategy must not create another semantic, styling, token, or accessibility contract.

Native token delivery

Platform source from the same graph, without a JavaScript runtime

pnpm build:native-tokens prepares the validated token graph for native serialization.

The generated native distribution includes Swift support/types/token files, Kotlin / Compose support/types/token files, per-theme variant files, a platform-map.json, and a native-distribution.manifest.json.

The native pipeline currently distributes token decisions only. It is not evidence that Concord ships native iOS or Android component libraries.

Runtime boundary

Choose the smallest interface that fits the product architecture

Different interfaces carry different runtime costs.

The static distribution requires no component framework runtime. Lit consumers add the custom-element delivery runtime where needed. React consumers add React ergonomics on top of the Lit layer. Native token consumers receive generated platform token source rather than a JavaScript runtime.

Consumers should choose the smallest interface that matches the application architecture rather than standardizing every product on the heaviest delivery path.

Static HTML & CSS No component framework runtime Optional framework-neutral behavior only where required
Lit Web Components Lit custom-element runtime Use where a custom-element boundary adds value
React adapters React + Lit delivery layers Use for typed React consumption, not as a new system implementation
Native tokens Generated platform source No JavaScript component runtime

Evidence boundary

Repository contracts are not the same as public release channels

The current repository proves workspace package contracts and generated distributions, not a public package release channel.

All current workspace packages are private. The static distribution is generated inside the repository. Native token artifacts are generated into the token package distribution tree.

Do not describe npm, Swift Package Manager, CocoaPods, Maven, Gradle, or another public registry/release workflow as a current Concord capability unless that publication pipeline is implemented and verified.

Repository proves Workspace packages · exports · generated static distribution · generated native token files · manifests
Repository does not currently prove Public npm release · SwiftPM/CocoaPods release · Maven/Gradle release · native component libraries

Decision guide

Select by consumer need, not organizational preference

Choose the smallest delivery interface that satisfies the consumer architecture. Delivery choice changes packaging, registration, runtime cost, and framework ergonomics; it does not change the underlying Concord contract.

Optimize for Consumer architecture
Minimize Unnecessary runtime and adapter layers
Preserve Shared semantics, tokens, CSS, accessibility, and behavior
Need canonical platform markup?Static HTML & CSSSmallest web delivery surface
Need a custom-element API?Lit Web ComponentsUse explicit custom-element delivery
Need typed React ergonomics?React adaptersConsume the shared Lit delivery layer
Need native design decisions?Generated token sourceSwift or Kotlin / Compose
The thinnest viable delivery layer wins.

A delivery layer may translate syntax, registration, packaging, event shape, type representation, or framework ergonomics.
