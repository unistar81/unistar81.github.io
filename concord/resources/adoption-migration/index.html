Resources / Adoption

Adoption & Migration

Adoption turns Concord from a reusable system into a working product dependency. Use the smallest supported delivery boundary, coexist before replacement, validate a bounded integration, return recurring friction upstream, and scale only after the shared contract survives real use.

Architectural

Adoption thesis

Adoption is a system outcome, not a rollout afterthought

Concord reduces adoption cost by keeping delivery choice, source ownership, namespace transformation, quality evidence, and product responsibility explicit.

A reusable system is not complete when shared code exists. It must be possible for teams to integrate the system, validate it under real product constraints, migrate without unnecessary rewrites, and return adoption evidence to the shared contract.

Repository mechanics prove Concord’s supported integration surfaces. Pilot cadence, organizational enablement, adoption targets, and product telemetry remain operating-model concerns rather than automated repository features.

Architecture Reduce coupling before rollout Framework-neutral contracts and multiple delivery paths lower the cost of entry.
Adoption Prove the contract in a real consumer Coexist, integrate, validate, learn, and expand without creating another source of truth.
Feedback Return friction upstream Repeated consumer pain is evidence about architecture, documentation, or ownership.

Adoption boundary

Start with the smallest supported interface that fits the product

Adoption should not require a framework migration when Concord already exposes a thinner compatible boundary.

Platform-native web Static HTML & CSS Canonical markup, authored CSS, optional framework-neutral behavior, examples, and manifests.
Web Component Lit custom elements Add a custom-element interface where that boundary improves product integration.
Framework adapter React adapters Use typed React ergonomics without redefining the underlying component system.
Platform decisions Swift + Kotlin / Compose tokens Distribute design decisions without claiming native component implementations.
Delivery choice is an adoption decision, not a design-language fork.

The same semantics, token meaning, visual contracts, accessibility expectations, and ownership rules remain upstream. Review the Delivery Model →

Coexistence & migration

Coexist before replacement

A bounded migration can introduce Concord without forcing an application-wide rewrite.

The static distribution can transform token-variable and component-class prefixes at build time. The same transformation propagates through authored CSS, canonical HTML, cascade layers, and the generated component catalog.

Namespace isolation helps contain technical collisions during coexistence. It does not automatically resolve semantic differences, product composition, or the decision to retire an older local contract.

Current product Bounded coexistence window Retained shared path
  1. 01 Existing product system Keep current behavior stable while the migration boundary is defined.
  2. 02 Scoped Concord distribution Choose default, custom, split, or unprefixed naming according to coexistence needs.
  3. 03 Bounded pilot Integrate one real surface instead of replacing the application wholesale.
  4. 04 Validated expansion Broaden adoption only after quality and integration evidence are acceptable.
  5. 05 Retire replaced local contracts End coexistence deliberately when consumers no longer need the old path.
Repository default dsl tokens · dsl classes Canonical Concord naming.
Common prefix --prefix=<name> Transform token variables and component classes together.
Split prefixes --token-prefix + --class-prefix Transform token and component namespaces independently.
No prefix build:distribution:unprefixed Generate the repository-verified unprefixed variant.

Reference environment

The documentation environment must consume the system it explains

Concord’s reference surfaces are useful because they exercise canonical sources and delivery contracts rather than replacing them.

Component documentation resolves repository data, canonical scenarios, source paths, Lit examples, React examples, and component-reference data. Storybook and the generated static showcase provide additional repository-backed views over the same system.

Pilot-first operating model

Pilot before scaling

A bounded pilot converts adoption from an assumption into evidence.

  1. 01
    Bound the surface Choose one meaningful product area with real content, interaction, and layout pressure.
  2. 02
    Choose the delivery boundary Use the smallest supported interface that matches the product architecture.
  3. 03
    Integrate under real constraints Exercise theme, density, content, responsive behavior, accessibility, and surrounding product code.
  4. 04
    Return friction upstream Treat repeated integration work as evidence about APIs, ownership, documentation, or missing system capability.
  5. 05
    Expand after evidence Scale adoption only after the shared contract survives a real consumer without requiring a fork.
Evidence gate Expand scope only after the shared contract survives real consumer pressure.
Operating model, not repository automation.

Concord supplies the architectural boundaries and validation surfaces. Product selection, rollout sequencing, enablement, and organizational approval remain context-specific responsibilities.

Adoption evidence

Measure integration quality, not package presence

Repository checks and organizational adoption measures answer different questions.

Concord can prove build integrity, canonical-source relationships, accessibility contracts, browser behavior, responsive containment, and other repository-defined quality gates. Product adoption requires additional evidence from the consuming organization.

Repository-verifiable
Canonical source fidelityDocs and adapters remain downstream of shared contracts.
Build + validation integrityGenerated artifacts and focused tests remain reproducible.
Quality contractsAccessibility, compatibility, content resilience, and responsive behavior are testable.
Organization-measured
Time to successful integrationHow much work is required before a product can use the system correctly?
Migration and exception rateHow much local code, override, or fork remains during adoption?
Recurring consumer frictionWhich support questions and workarounds repeat across teams?
Do not fabricate adoption telemetry.

Organization-level measures require product or enterprise instrumentation. They are evaluation criteria here, not claimed Concord analytics.

Feedback as architecture evidence

Recurring friction is a system signal

Adoption feedback becomes valuable when it is routed to the responsibility that can remove the friction for more than one consumer.

Observed friction Architecture question Likely review boundary
Repeated local overrides Is shared visual intent missing from tokens, CSS, or component configuration? Token / component ownership
Framework-specific workaround Is delivery ergonomics missing, or is the shared contract incorrectly framework-coupled? Delivery Model
Copied canonical markup or CSS Why can the consumer not use the canonical source directly? Source ownership
Recurring integration question Is the supported path unclear, incomplete, or hidden? Documentation
Product-local feature requested globally Is the responsibility genuinely shared across consumers? Contribution Model
Friction should produce a decision, not an undocumented workaround.

Shared needs can enter the Contribution Model; responsibility questions belong in Ownership.

Federated adoption

Federate responsibility without fragmenting the source of truth

Enterprise scale does not require every product decision to move into the core system.

Concord’s ownership model supports a central shared contract while applications retain product-local state, workflow, data, and business rules. Organizations may add named maintainers, councils, approval routing, SLAs, training, or business-unit policies on top; the current repository does not encode those structures.

Shared core Canonical system contracts Tokens, semantic components, authored CSS, layout, shared behavior, accessibility, delivery contracts.
Product responsibility Local composition and business truth Application state, routing, data, permissions, workflow, and product-specific decisions.
Optional organizational overlay People and process around the architecture Teams, councils, training, SLAs, approval rules, and adoption targets only where an organization defines them.

Failure signals

Adoption is failing when integration creates another system

These signals indicate that migration, ownership, or delivery boundaries need review.

Signal What it indicates
01 Parallel local systems Products rebuild shared controls instead of consuming or contributing upstream.
02 Framework capture Adoption requires changing frameworks rather than choosing a compatible delivery boundary.
03 Unbounded overrides Local CSS silently becomes the real design language.
04 Copied canonical source Markup or CSS is duplicated because the supported source cannot be consumed directly.
05 Migration without an exit Old and new systems coexist indefinitely without a retirement decision.
06 Install = adoption Package presence is counted as success without evidence that teams can integrate and maintain the contract.

Adoption record

Make the migration boundary legible before rollout expands

A durable adoption decision records enough context for the next team to understand what is being introduced, preserved, validated, and retired.
