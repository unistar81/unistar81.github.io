System Architecture

Concord separates design decisions, semantic structure, presentation, behavior, and delivery interfaces so each layer can evolve without forcing the others to be rewritten.

Architecture thesis

One language. Explicit ownership. Multiple delivery interfaces.

One shared design language should survive changes in framework, product, theme, density, and delivery technology.

Platform token distribution

One token graph, three sibling platform outputs

Concord prepares the canonical token graph once, then generates platform-specific distribution artifacts without creating separate authored token systems.

CSS consumes the authored/reference-bearing view so intentional alias relationships remain visible at runtime. Swift and Kotlin consume resolved build-time variants appropriate to native token packages.

Canonical source Validated token graph Foundation → System → Semantic → Component
Shared preparation Platform-neutral prepared graph Authored view · resolved view · provenance · theme/density context
Web CSS Generated custom properties
iOS Swift Generated token package
Android Kotlin / Compose Generated token package
Dependency rule Native output never sits upstream of CSS

Removing a native target must not change canonical token JSON or the public web runtime contract.

Design rule Emitters translate; they do not invent

Platform naming, syntax, types, namespaces, and serialization may differ without introducing new design decisions.

Scope boundary Tokens, not native component libraries

Swift and Kotlin output distribute design decisions; native iOS/Android components are not implied by those packages.

Web static distribution

Build-time tooling, framework-free web consumption

The static distribution is a first-class delivery target.

It is generated from canonical token data and authored system sources so a consuming application can use generated token CSS, core CSS, component CSS, semantic HTML, and framework-neutral behavior without requiring React, Lit, Node.js, or runtime token compilation.

Build-time tooling creates the artifacts. Browser consumption does not require the build toolchain.

Separation of concerns

Each layer owns one kind of responsibility

Architecture stays coherent when a concern changes at its source instead of being copied into every delivery technology.

Design language system owns Shared experience contracts

design decisions · semantic component contracts · layout/composition rules · external CSS · accessibility · component-owned behavior · delivery adapters

Consuming product owns Application and business concerns

routing · data fetching · domain rules · analytics · application state · product-specific orchestration and composition

Responsibility boundary Keep the boundary explicit.

The system can provide reusable structure and interaction contracts without absorbing product business logic. Avoid moving responsibilities across these boundaries merely for framework consistency or implementation convenience.

Component host architecture

Choose the host by semantic responsibility

Concord does not require every named component to use a custom-element host.

Use a native element as the canonical static host when the platform already provides the correct semantic or behavioral primitive. Current examples include:

A Lit API does not automatically choose the static host.

The canonical host follows the component’s semantic and architectural role. Delivery technology follows that decision rather than redefining it.

Progressive delivery

One component identity can support authored and managed light DOM

Canonical custom-host components support progressive delivery.

Consumer-authored canonical light DOM is preserved when an approved custom host upgrades after Lit registration. An empty host created by a Lit or framework adapter can render managed light-DOM anatomy from adapter properties.

Both paths preserve the same semantic, token, CSS, accessibility, and component-behavior contracts.

Same component contract Two compatible initialization states

Delivery changes; semantic, token, CSS, accessibility, and behavior contracts do not.

Consumer-authored host Preserve existing canonical light DOM

Upgrade the authored host without replacing valid consumer-provided structure.

Empty adapter-created host Render managed light-DOM anatomy

Adapter properties can produce the same component contract when no authored structure exists.

Architecture guardrails

Protect the shared language at its boundaries

Guardrails turn the architecture from a diagram into a review model for design, engineering, accessibility, and product decisions.

01 Prefer web-platform semantics before abstraction.
02 Keep generated artifacts reproducible from canonical sources.
03 Keep presentation in shared external CSS rather than framework-specific copies.
04 Add behavior only where the platform stops.
05 Use custom hosts only for meaningful system-owned boundaries.
06 Treat frameworks as delivery machinery around the shared contract.
07 Keep application state outside the component contract unless the component explicitly owns that state.
08 Fix ownership problems at their source rather than patching documentation-only implementations.

Enterprise intent

Treat the design language as product infrastructure

A mature design language system is more than a component catalog. It is shared product infrastructure connecting design decisions, semantic implementation, accessibility, delivery technology, documentation, and governance.

Concord’s architecture keeps those responsibilities explicit so teams can change frameworks, themes, products, delivery paths, or platform token targets without fragmenting the language they share. Framework-independent layout, sibling Web/iOS/Android token distribution, and clear separation from product logic reduce integration friction without turning one application or platform architecture into the system architecture.
