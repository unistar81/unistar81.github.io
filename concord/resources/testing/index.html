Resources / Quality

Testing

Concord treats testing as an evidence architecture for shared-system change. Different checks protect source contracts, generated artifacts, browser behavior, documentation, and compatibility environments; no single passing suite is allowed to stand in for all of them.

Quality thesis

Test the contract where it can fail

Test the contract at the boundary where it can fail.

Concord does not organize quality around a ceremonial test pyramid. A token reference can fail before rendering, generated output can drift while source tests still pass, browser behavior can regress after a valid build, and documentation can misrepresent an otherwise-correct implementation.

The useful question is therefore not only "did the tests pass?" It is "which contract was exercised, at what boundary, and what claim does that evidence actually support?"

Shared-system change Tokens · HTML · CSS · behavior · adapters · docs Different changes cross different evidence boundaries.
Source & build evidence Runtime & product evidence Support evidence
01 · Static Type correctness Repository TypeScript
02 · Contract Source invariants Token · manifest · architecture · documentation
03 · Artifact Generated integrity CSS · manifests · static · native
04 · Browser Rendered behavior Semantics · geometry · keyboard · state
05 · Product surface Built documentation Astro + Playwright
06 · Compatibility Engine evidence Chromium · Firefox · WebKit
Evidence rule A passing layer proves the boundary it exercised—not the entire system.

Validation topology

One core gate. Specialized gates stay explicit.

pnpm validate is the current core repository validation bundle.

It runs TypeScript type checking, the main Vitest suite, generated token currency checks, generated style currency checks, component-manifest currency checks, and formatting verification.

The main pnpm test step first builds web tokens, authored styles, and Lit, then runs the Vitest Node and browser projects.

The core validation command is important, but it is not an umbrella for every repository surface.

Generated-artifact evidence

Prove the output, not only the generator

Generated output is part of the product surface and receives its own evidence.

The static-distribution tests verify a complete framework-neutral artifact: token CSS, authored CSS, canonical snippets and compositions, optional behavior files, examples, component manifests, and the outer distribution manifest.

Browser evidence

Rendered contracts need a real browser

The default Vitest browser project runs package and tooling *.browser.test.ts files in headless Chromium at a 1280 × 720 viewport.

The browser layer is where Concord proves behavior that source inspection cannot establish by itself: geometry, focus, keyboard interaction, native state styling, content containment, adapter behavior, computed CSS, and component-level contrast.

Product-surface validation

The documentation application is tested as a product

Concord treats its documentation application as part of the system interface rather than passive prose.

pnpm validate:docs regenerates documentation inputs, type-checks and builds the framework adapter path used by the site, runs Astro validation and static build, and then serves the built output to Playwright.

The documentation Playwright configuration uses Desktop Chrome, retains traces on failure, and runs against the built preview rather than development HMR state.

Focused suites protect Resources, Foundations, Patterns, Templates, appearance environments, canonical examples, and other documentation contracts. Documentation regressions therefore protect both teaching accuracy and the product surface through which consumers learn the system.

Compatibility evidence

Multi-engine checks inform support; they do not define it

The dedicated compatibility configuration executes the same package/tooling browser-test family across Chromium, Firefox, and WebKit.

It can accept explicit browser executable paths for reproducible historical-engine checks and can apply forced-colors or reduced-motion context overrides through environment variables.

The configuration itself states the intended evidence boundary: compatibility runs are capability evidence, not a declaration that the configured browser versions define Concord's support policy.

Compatibility evidence should inform a support decision; it should not silently become the support decision.

Engine 02 Firefox Same browser-contract family
Engine 03 WebKit Same browser-contract family
Dedicated evidence command pnpm test:compatibility Serial execution through the compatibility configuration

Capability evidence ≠ support declaration.

The compatibility configuration deliberately keeps executable evidence separate from the policy decision about which engines and versions Concord officially supports.

Quality ownership

Evidence is shared; responsibility remains explicit

Testing is shared work, but ownership is not interchangeable.

Operating rule Put reusable evidence with the shared system; keep product validation with the product.
Design Define the behavior and visual-state intent worth protecting
Engineering Implement executable source, build, browser, adapter, and artifact evidence
System stewardship Shape gates, evidence boundaries, and canonical regression policy
Consuming product Validate workflows, real content, product accessibility, performance, and release integration

Evidence boundary

Do not turn available checks into claims they do not support

The current repository proves executable validation commands and a broad set of source, generation, browser, documentation, and compatibility checks.

Repository proves Executable source, artifact, browser, documentation, and compatibility validation surfaces
CI enforcement Not proven by the collected source No .github/workflows validation workflow was collected.
Coverage threshold Not a current release gate test:coverage exists; no percentage threshold is configured.
Core validation scope pnpm validate is not the universal umbrella Docs · native tokens · compatibility · Storybook · version remain explicit gates.
The useful claim is not “everything is tested.”

The defensible claim is stronger than "Concord has tests": Concord places executable evidence at multiple boundaries where shared-system change can fail, and it keeps the scope of each claim explicit.
