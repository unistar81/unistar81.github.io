Template state note

The criteria remain while the collection slot changes

The application chooses the current state; Concord Patterns determine how waiting, known-zero, and failure are communicated.

Loading Loading & Progress replaces results while the outcome is unknown.
Known zero Empty States replaces results and Pagination while criteria remain available.
Failure Status and recovery replace results without erasing query context.

Composition boundary

List / Index Page owns page-scale collection composition, not search logic, collection rendering, or pagination mechanics. The Template decides how page identity, page actions, criteria, result feedback, the collection slot, and collection navigation relate spatially and semantically.

Search & Filtering owns the relationship among query controls, structured criteria, applied state, result feedback, and the reduced collection. Empty States owns known-empty recovery. Loading & Progress owns meaningful waiting. Pagination owns the relationship among the paged collection, range context, and page destinations, while the Pagination component owns the navigation control itself.

Field, Input, Selectable Pill, List Item, Link, Button, and other Components retain their canonical contracts. The consuming application owns query execution, matching and ranking, routes, result data, totals, authorization, caching, page-window calculation, persistence, and product-specific actions.

Do not introduce a `dsl-list-index-page` component or a Template-specific search, result-row, or pagination API merely to package this composition.

Page anatomy & hierarchy

  • Page identity comes first. Give the collection a clear route title and concise purpose before presenting controls or results.
  • Keep page actions distinct from collection criteria. Create, import, export, or other page-level actions may share the title region, but they do not become search filters merely because they affect the same collection.
  • Criteria precede the collection they reduce. Search and filter controls should remain adjacent to the result scope they affect without becoming part of every result row.
  • Result feedback bridges criteria and content. A concise count or state summary helps users understand what the current criteria produced.
  • The collection slot owns one current presentation. Loaded results, meaningful loading, a known-empty state, unavailable content, or recoverable failure replace one another within the same page region.
  • Collection navigation follows the collection. Pagination belongs after the result set it navigates and disappears when no additional pages exist.

Query, filters & applied state

  • Compose the canonical Search & Filtering Pattern. Use a labelled search Input for free-text intent and appropriate controls for structured dimensions; do not invent Template-level control variants.
  • Keep applied criteria discoverable. Users should be able to determine which query, filters, and sort state produced the visible collection without reopening hidden controls.
  • Keep independent filters independently operable. Selectable Pills remain native checkbox semantics; exclusive criteria require an appropriate exclusive-selection control.
  • Choose an application model deliberately. Query submission, considered debounce, immediate filters, or an explicit Apply action are product decisions, but one collection should behave predictably.
  • Reset invalid dependent navigation. A materially changed query or filter set should normally return the collection to its first valid page rather than preserving a page that no longer exists.
  • Preserve shareable state when useful. Bookmarkable collection views should consider representing stable query, filter, sort, and page state in application-owned destinations.

Result feedback & collection states

  • Keep result feedback close to the collection. A count or concise summary should describe the state users are about to inspect.
  • Loaded results keep their own component semantics. List Item, Card, table, or another supported presentation continues to own each item's rendering.
  • Unknown is not empty. When the application does not yet know the result, compose Loading & Progress in the collection slot rather than showing an Empty State.
  • Known zero uses Empty States. Preserve still-useful query/filter context and replace only the missing collection content with the appropriate explanation and recovery.
  • Failure is not zero results. Preserve query and filter context, communicate the failure, and provide a recovery path without masquerading as an empty collection.
  • Unavailable content explains the known reason. Permission, disconnected data, or another known restriction may use an unavailable/restricted Empty State when the application can explain the condition.
  • Do not keep stale Pagination below a zero state. When the result has no pages, remove the collection-navigation control while leaving relevant criteria available.

Results, selection & row actions

  • Choose a collection presentation for the information shape. List Item is appropriate for concise navigable records; Card, table, or another existing component may be better for richer or strongly tabular content.
  • Keep the whole-row destination understandable. When a result navigates to one clear destination, a linked List Item can expose that destination without adding a redundant View button.
  • Do not infer selection from navigation. Row activation and multi-select are different interaction models. Add selection only when the product actually supports selected-set actions.
  • Keep bulk action state application-owned. A Template may provide a place for selected-set actions, but selected IDs, eligibility, persistence, and action outcomes belong to the product.
  • Preserve deterministic ordering while paging. When stable numbered pages are presented, the application should use an ordering model that prevents records from unpredictably moving between pages during ordinary navigation.

Pagination, routes & history

  • Paginate the reduced result set, not the source collection. Query, filters, and sort determine the collection before Pagination divides it.
  • Use real destinations for page navigation. Previous, Next, and page numbers should preserve normal link behavior, browser history, copyable destinations, and new-tab behavior.
  • Keep the current page non-interactive. Use canonical current-page semantics instead of linking users back to the location they already occupy.
  • Preserve collection-defining state in every destination. Page navigation must not silently drop query, filters, sort, page size, or other stable collection context.
  • Do not claim totals the application cannot support. Use Previous/Next or another appropriate model when a stable total is unavailable rather than manufacturing page counts.
  • Keep route restoration meaningful. Back and Forward should restore an understandable collection state when the product exposes query/filter/page state through application routing.

Loading, focus & asynchronous replacement

  • Keep meaningful loading scoped to the result region. Criteria and useful surrounding context should normally remain available while the collection changes.
  • Prevent stale responses from replacing newer intent. Applications should cancel, ignore, or reconcile out-of-order query and page responses.
  • Do not move focus merely because results refresh. Keep focus on the search, filter, sort, or pagination control the user operated unless a documented recovery interaction requires otherwise.
  • Treat page activation as navigation. Full navigation may use normal browser behavior; client-side routing should preserve equivalent destination and focus semantics.
  • Announce meaningful result changes politely when needed. A stable status relationship may report the resulting count after asynchronous updates without announcing every transient keystroke or loading frame.
  • Avoid layout flicker for trivial work. Do not flash a loading treatment for operations that complete immediately, but do not delay feedback so long that the interface appears unresponsive.

Responsive composition & content resilience

  • Preserve one semantic source order. Page title, actions, criteria, result feedback, results, and Pagination should remain meaningful in reading and keyboard order while spatial relationships wrap or stack.
  • Let actions and criteria wrap before they compress. Do not shrink labels, hit targets, or Inputs below useful measures merely to preserve a desktop row.
  • Keep search measure intentional. The search field may occupy a useful bounded measure while remaining fluid inside the available page width.
  • Allow filter sets to grow. Additional criteria, localization, and longer labels should wrap through the owning Pattern rather than causing horizontal page overflow.
  • Keep result content resilient. Long titles, metadata, supporting text, and user-generated strings must wrap through the collection component's own contract.
  • Let Pagination use its canonical wrapping behavior. Do not replace it with a different mobile control solely because the page becomes narrow.

Accessibility & collection orientation

  • Use a useful heading hierarchy. The route title identifies the page; criteria and result scopes need headings or labels when necessary for orientation.
  • Keep Search a named search landmark. The search form should communicate its purpose without relying only on placeholder text or an icon.
  • Preserve native control semantics. Search Input, checkbox-based Pills, links, Buttons, and Pagination retain their keyboard and accessible-name behavior.
  • Keep result-count announcements scoped. Dynamic result updates may use a stable polite status relationship; the entire page must not become a live region.
  • Do not duplicate controls for breakpoints. Parallel desktop/mobile criteria create duplicate names, focus stops, and state unless the product deliberately owns a synchronized alternate-control model.
  • Keep recovery actions reachable in the collection slot. Empty, unavailable, and failure recovery should appear where users expect the missing results rather than moving them to an unrelated page region.

Application ownership & state integrity

  • Query execution remains application-owned. Tokenization, debounce timing, server requests, matching, ranking, and search-service behavior are not Template APIs.
  • Data truth remains application-owned. Result rows, counts, totals, permissions, sort keys, cursor state, and page validity come from the consuming product.
  • Authorization remains application-owned. The Template can preserve a place for restricted-state communication but does not decide which records or actions a user may access.
  • Routing remains application-owned. Concord requires meaningful destinations and preserved state; it does not prescribe URL syntax or a router.
  • Caching and persistence remain application-owned. Saved views, remembered filters, query history, and cached pages are product features unless a separate Concord contract explicitly defines them.
  • Mutations remain application-owned. Creating, deleting, exporting, or bulk-updating records may affect the collection, but their business rules and outcomes do not move into the Template.

Theme, density & page-scale validation

The same List / Index Page should remain understandable across supported themes, light and dark appearance, density settings, localization, zoom, long content, and narrow available widths.

Theme and appearance may change resolved presentation. Density may change control compactness and spacing. Neither should change semantic source order, which criteria are active, which page is current, whether an item is selected, or which action is primary.

This Template therefore validates a demanding cross-section of Concord at page scale: Layout, form composition, selection controls, List Item, Link, Button, Search & Filtering, Loading & Progress, Empty States, Status Messaging, and Pagination must coexist without Template-specific forks.
