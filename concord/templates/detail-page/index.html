Accessibility guidance

Interaction, content, and implementation guidance for accessible workspace experiences.

Overview

This document defines the accessibility expectations shared by workspace interfaces. It keeps semantic structure, keyboard access, focus behavior, status communication, and content resilience aligned across implementation layers.

Product teams keep ownership of their workflow decisions while the design system provides reusable contracts for controls, layout, feedback, and interaction behavior.

Key requirements

  • Preserve meaningful semantic source order.
  • Keep keyboard and focus behavior predictable.
  • Communicate dynamic status without relying on color alone.
  • Support localization, zoom, and long user-generated content.

Implementation notes

Framework adapters may provide delivery ergonomics, but they do not replace the semantic HTML, CSS, token, and behavior contracts that define the system.

Template state note

Keep record identity while workflow state changes

Loading, unavailable, failure, and mutation outcomes compose existing Feedback and Empty State Patterns rather than changing the Detail Page into a stateful record component.

Loading Use Loading & Progress while record truth is still unknown.
Unavailable Explain a known restriction and preserve useful route context.
Save failure Keep identity and valid user work while Status Messaging provides recovery.

Composition boundary

Detail Page owns page-scale record composition, not the record model, component internals, or workflow business logic. The Template establishes how breadcrumb context, record identity, page actions, metadata, primary content, and complementary information relate semantically and spatially.

Breadcrumb owns hierarchical navigation. Action Groups owns priority among related actions. Confirmation owns deliberate decision points for consequential actions. Status Messaging communicates meaningful workflow outcomes. Popover and Modal retain their own disclosure and focus contracts when a product needs them.

Link, Button, List Item, Divider, and other Components keep their canonical semantics, state, behavior, and public configuration. Concord Layout owns reusable spatial relationships such as Flow, Split, Sidebar, Region, and Content Boundary.

The consuming application owns record data, routes, authorization, edit state, validation, persistence, optimistic updates, mutations, audit history, and product-specific business rules.

Do not introduce a `dsl-detail-page` component, Record component, or Template-specific metadata/action API merely to package this composition.

Record identity & hierarchy

  • Preserve hierarchical context. Use Breadcrumb when the record belongs to a navigable hierarchy or collection users may reasonably return to. Do not add Breadcrumb merely as decoration.
  • Keep one clear page title. The record's human-readable name should be the route title and primary heading. IDs, types, and status belong in supporting metadata unless they are the only meaningful identity.
  • Keep descriptive context close to the title. A concise record type, summary, or status may support orientation without competing with the title.
  • Do not make metadata carry the page identity. Users should not need to scan an owner, timestamp, or internal identifier to understand which record they are viewing.
  • Preserve stable identity through state changes. Saving, refreshing, or displaying a recoverable error should not silently replace the route title with a generic workflow label.

Page actions, editing & confirmation

  • Use one clear primary action per decision region. An action such as Edit document may lead the page action group while lower-emphasis peers remain secondary.
  • Keep action meaning explicit. Prefer outcome-oriented labels such as Edit document, Share, Archive, or Delete rather than generic labels such as Manage or Submit.
  • Do not make every action primary. Equal visual emphasis implies equal priority and weakens the page hierarchy.
  • Keep destructive actions semantically separate from danger. Destructive styling does not determine whether an action is primary. Confirmation is warranted by consequence, reversibility, scope, and user expectation.
  • Use Confirmation for consequential commitment, not routine clicks. The Detail Page may compose Confirmation inline or through Modal when blocking background interaction is warranted; the Template does not redefine either Pattern.
  • Keep pending work application-owned. Disable or constrain only controls whose repeated activation would be unsafe while a mutation is in progress.
  • Return outcomes through existing feedback contracts. Success, failure, warning, and recovery belong to Status Messaging and Form Validation rather than a Detail-specific save state.

Metadata & status

  • Use semantic description structure for label/value data. A native definition list is appropriate when metadata consists of concise terms and values.
  • Keep metadata useful. Owner, status, last updated, identifier, and similar values should help users interpret or act on the record rather than merely expose storage fields.
  • Treat status according to meaning. A concise record status can remain ordinary metadata. Use Alert or Status Messaging only when a condition needs workflow feedback or announcement behavior.
  • Do not encode meaning through color alone. If status or state uses visual reinforcement, the text must still carry the meaning.
  • Allow values to wrap and localize. Long names, identifiers, dates, translated labels, and generated content must not force the metadata region to create horizontal overflow.
  • Keep audit history distinct from summary metadata. A detailed event timeline or activity log is its own content relationship, not an excuse to overload the compact metadata block.

Primary & supporting content

  • Keep the record's substantive content primary. Supporting metadata, related records, history, or contextual guidance should not visually compete with the main content users came to inspect.
  • Use Sidebar only for a genuine primary/supporting relationship. A narrow visual column does not automatically become complementary content; use `aside` only when its meaning is actually complementary.
  • Use a readable measure for long-form content. Narrative copy should not stretch merely because the page has wide available space.
  • Allow sections to grow independently. Long headings, lists, notes, user content, and embedded Patterns should wrap without requiring synchronized region heights.
  • Preserve component ownership inside regions. Related records may use canonical List Item; links, buttons, alerts, media, or other controls retain their own contracts.
  • Avoid ornamental cards around every section. Surface treatment should communicate a useful boundary rather than turning every piece of record content into an unrelated panel.

Related records & contextual navigation

  • Keep related content genuinely related. Related records should help users continue the current task or understand the current item, not become a generic recommendation surface.
  • Use real destinations. Related records and Breadcrumb ancestors remain links with normal browser navigation semantics.
  • Preserve collection context when useful. A route returning to a filtered collection may retain stable application-owned query/filter/page state when doing so improves orientation.
  • Do not replace Breadcrumb with browser history. A Back control and hierarchical navigation answer different questions; products may support both when their semantics are clear.
  • Keep related-item anatomy canonical. List Item or another collection component continues to own row semantics, focus, and content anatomy.

Record state, loading & recovery

  • Unknown is not unavailable. When the application is still fetching the record, compose Loading & Progress rather than implying the record is absent or inaccessible.
  • Unavailable content explains a known condition. Authorization, disconnected data, or another known restriction should communicate the reason and any recovery users can take.
  • Not found or deleted is a route outcome. A missing record may require an Empty State or route-level recovery, but it must not masquerade as a transient loading state.
  • Recoverable failure preserves orientation. When refresh or save fails, keep record identity and still-valid user context available whenever possible and communicate the next useful action.
  • Stale data should be explicit when material. If the application knows the visible record is out of date, communicate that condition and recovery rather than silently replacing user work.
  • Do not invent Template-level loading or persistence flags. The consuming application decides state truth; the Template provides composition slots for the appropriate existing Patterns.

Responsive composition & source order

  • Author one meaningful source order. Breadcrumb, title, actions, primary content, metadata, and related information should remain understandable before responsive presentation is applied.
  • Let actions wrap before they compress. Keep readable labels and usable targets rather than forcing page actions to remain in a single row.
  • Use intrinsic Sidebar wrapping for primary/supporting regions. Supporting metadata should move below the primary content when useful side-by-side space no longer exists.
  • Preserve the record title and primary action hierarchy at narrow widths. Reflow may change placement but not which action is primary or which heading identifies the page.
  • Keep long content resilient. User-generated strings, IDs, URLs, metadata values, and related-item labels must wrap without horizontal page overflow.
  • Avoid device-named Detail variants. Relationships should change because available space and content require it, not because the Template has become a separate phone or tablet page.

Accessibility, focus & interaction

  • Use landmarks deliberately. The record's primary content belongs within the page's existing main landmark; complementary content may use `aside` when its role is truly complementary.
  • Preserve heading hierarchy. The record title is the page heading; content-region headings describe sections beneath it without choosing heading levels for visual size.
  • Keep Breadcrumb named and ordered. The canonical Breadcrumb uses a named navigation landmark, ordered list, Link ancestors, and a non-interactive current page.
  • Do not move focus merely because record data refreshes. Focus remains with the active control unless a route transition, Modal, validation error, or recovery Pattern has its own established focus behavior.
  • Return focus predictably from disclosure. Popover and Modal own their canonical dismissal and focus-return contracts when composed from the Detail Page.
  • Support zoom, localization, and keyboard use. Metadata, actions, related content, and long record copy must remain operable and understandable without clipping or visual-only ordering.

Application ownership & mutation integrity

  • Record truth remains application-owned. Field values, status, owner, timestamps, permissions, related-record logic, and history come from the consuming product.
  • Authorization remains application-owned. Concord can compose how restricted or unavailable information is communicated; it does not decide who may view or mutate the record.
  • Routing remains application-owned. Breadcrumb and related records require meaningful destinations, but Concord does not prescribe URL syntax, route loaders, or router technology.
  • Validation and persistence remain application-owned. Form contracts can communicate invalid input, but save rules, concurrency, optimistic updates, rollback, and durable storage remain product responsibilities.
  • Mutations remain application-owned. Edit, archive, delete, duplicate, share, or other record actions may use Concord action and confirmation Patterns, but their business rules and side effects remain outside the Template.
  • Concurrency decisions remain application-owned. Version conflicts, stale writes, record locking, and merge strategies must not be hidden inside a page-composition API.

Theme, density & page-scale validation

The same Detail Page should remain understandable across supported themes, light and dark appearance, density settings, localization, zoom, long record content, and narrow available widths.

Theme and appearance may change resolved color and surface decisions. Density may change spacing and control compactness. Neither should change record identity, source order, action priority, metadata meaning, Breadcrumb hierarchy, or which content is primary versus supporting.

Detail Page therefore provides another page-scale integration proof that Foundations, Layout, Components, and Patterns can compose into a focused enterprise record view without Template-specific component forks.
