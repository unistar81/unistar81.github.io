Template state note

Keep application state ownership outside the Template

Dirty state, validation truth, saving, persistence, authorization, and success or failure remain application-owned. The Template defines where those states participate in the page composition.

Validation Keep correction next to the affected field or group.
Saving Prevent unsafe duplicate submission without replacing page structure.
Failure Preserve valid user work and present a recoverable status.

Composition boundary

Settings Page owns the page-level relationship among section navigation, grouped preference regions, field composition, validation placement, and save actions. It does not own the internal contract of Input, Select, Toggle, Radio, Checkbox, Button, Form Field Group, Form Validation, or Status Messaging.

The consuming application owns settings data, authorization, persistence, dirty-state calculation, submission, optimistic or pessimistic update policy, server validation, conflict handling, and success or failure truth.

Do not introduce a `dsl-settings-page` component or a Template-specific settings API merely to package this composition.

Settings page anatomy & grouping

  • Give the page one clear title and concise explanation before the settings regions.
  • Group preferences by user-understandable purpose rather than by component type.
  • Keep section headings visible and meaningful even when a group contains only one setting.
  • Keep related controls close enough to read as one region while preserving enough separation between groups to scan a dense page.
  • Use existing Concord components inside each region rather than creating Template-owned field styles.

Section navigation & landmarks

  • Use section navigation when the page is long enough that direct movement among settings groups reduces effort.
  • Navigation targets must be real fragment destinations with stable section headings.
  • Keep source order understandable: page identity, section navigation, settings content, then page-level actions.
  • On narrow layouts, section navigation may move above the settings content; it must not duplicate controls or create a second state model.
  • Keep one primary `main` destination in the consuming shell; the Template specimen demonstrates internal page composition, not another application shell.

Field composition & validation

  • Keep labels, controls, supporting guidance, and errors in their canonical component or Form Layout relationships.
  • Place validation next to the field or group that needs correction. Do not summarize ordinary field errors only at the bottom of the page.
  • Preserve entered values when validation fails.
  • Do not use placeholder text as a replacement for a persistent label.
  • Required, optional, read-only, disabled, and policy-managed states must remain distinguishable in both semantics and presentation.

Immediate vs submitted preferences

  • Use Toggle for a setting that takes effect immediately only when the application can truthfully apply or revert that change at activation time.
  • Use Checkbox, Radio, Select, Input, and related form controls when changes belong to a later Save action.
  • Do not place an immediate Toggle inside a form and then imply that its state is pending Save unless the product explicitly defines that behavior.
  • If administrator policy prevents a change, keep the setting understandable and communicate why it is unavailable.

Save actions, dirty state & recovery

  • Keep one clear primary save action for a bounded set of submitted changes.
  • Disable or otherwise de-emphasize Save when there is nothing to commit only if the application can determine dirty state reliably.
  • Keep Cancel, reset, and navigation-away behavior semantically distinct. They are not interchangeable.
  • While saving, prevent unsafe duplicate submission and preserve enough page context for recovery.
  • On failure, keep valid user input and place recovery information near the affected workflow rather than erasing the form.
  • On success, Status Messaging may confirm the result without moving focus unnecessarily.

Responsive composition & content resilience

  • Preserve semantic source order while section navigation and settings content reflow.
  • Prefer intrinsic widths and wrapping to fixed desktop form columns.
  • Keep controls readable with long labels, localized text, text zoom, and fallback fonts.
  • Do not shrink interactive controls merely to keep a two-column layout.
  • Allow supporting descriptions and validation messages to wrap without overlapping controls or forcing horizontal page overflow.

Accessibility, focus & keyboard

  • Use native labels, fieldsets, legends, inputs, selects, buttons, and links where their semantics match the interaction.
  • Keep keyboard order aligned with meaningful source order.
  • Moving or stacking regions at narrow widths must not move focus or create duplicate focus targets.
  • Associate supporting and error text programmatically when it describes a control.
  • Do not announce every settings-region update. Live-region behavior belongs to meaningful asynchronous status changes, not ordinary form navigation.
  • Return focus deliberately only when a Modal, Popover, validation recovery path, or other participating Pattern requires it.

Application ownership & state integrity

  • Settings values remain application-owned.
  • Authorization and policy remain application-owned.
  • Persistence, caching, autosave, mutation retries, concurrency, and conflict resolution remain application-owned.
  • Server-side validation and business rules remain application-owned even when Concord Form Validation presents the resulting correction.
  • Routing and navigation-away protection remain application-owned.
  • The Template describes how those states are composed and communicated; it does not implement the product state machine.

Theme, density & page-scale validation

A Settings Page is a strong page-scale integration test because many controls appear together under one hierarchy.

Validate the same semantic page structure across supported themes, light and dark appearance, and density settings. Theme may change visual expression and density may change spacing or control compactness, but neither should alter labels, source order, field grouping, validation meaning, primary-action hierarchy, or application ownership.
