Dashboard Shell

Dashboard Shell demonstrates a semantic page frame with persistent navigation, a clear main destination, summary regions, supporting content, and responsive page composition. It is a composition recipe built from existing Concord contracts, not a Dashboard component.

Composition boundary

Dashboard Shell owns the relationship among page-level regions, not the internal contract of any region or control. The Template establishes meaningful landmarks, source order, page hierarchy, available-space relationships, and the placement of existing Components and Patterns.

Native elements provide the page meaning. Concord Layout provides region rhythm and content boundaries. The consuming application supplies real destinations, authorization, data, product state, and route content.

Do not introduce a `dsl-dashboard-shell` component or a second semantic tree merely to package this composition.

Shell anatomy

  • Header. Contains product-level identity and truly global controls when the consuming application needs them. The Template does not prescribe a branded header implementation.
  • Primary navigation. Exposes the application's major destinations. Use a labelled native `nav`; do not infer navigation semantics from a visual sidebar.
  • Main content. Provide one primary `main` landmark for the route content. The page title and primary task context belong here.
  • Summary regions. Compact summaries may precede deeper content when they help users understand the current page. They are ordinary sections, Cards, status content, or other existing contracts rather than a Template-specific summary API.
  • Complementary content. Use `aside` only when the content is genuinely complementary to the main region. A visually narrow column is not automatically an aside.
  • Footer. Include page- or product-level footer content only when the consuming experience needs it. Footer presence is not required merely to complete the shell.

Semantic source order & landmarks

  • Author meaning before placement. Header, navigation, main content, complementary content, and footer should remain understandable in DOM order before page-level CSS is applied.
  • Keep one main destination. A Dashboard Shell should expose one primary `main` landmark. Nested Components and Patterns must not create competing page-level main regions.
  • Name repeated landmark types. If a page contains more than one `nav` or `aside`, give each an accessible name that communicates its scope.
  • Keep page headings inside the main task context. The route title should orient the current page without relying on navigation selection alone.
  • Preserve heading hierarchy. Summary and content-region headings should describe their sections; do not choose heading levels for visual size.

Navigation & route ownership

  • Navigation destinations are real application routes. The Template demonstrates where primary and contextual navigation can live; it does not invent a router or destination model.
  • Current-location state belongs to navigation. Use the canonical current-page semantics supplied by the navigation contract rather than styling the selected destination as state with no programmatic meaning.
  • Do not duplicate navigation for responsive layouts. Prefer one meaningful navigation source. If a product deliberately provides an alternate compact control, the consuming application must keep names, state, destinations, and focus behavior synchronized.
  • Keep global and contextual navigation distinct. A shell may include both, but each needs a clear scope and accessible name. Do not merge unrelated destination sets only to fill a sidebar.
  • Route changes own focus and scroll recovery. Responsive reflow does not move focus. Client-side routing should restore orientation according to the consuming application's navigation policy.

Summary & content regions

  • Use summaries only when they reduce interpretation cost. Do not turn every page into a metric dashboard. Summary regions should answer useful questions about the current page or workflow.
  • Preserve the underlying component contracts. Cards, Lists, Alerts, Links, Buttons, and status content remain canonical Concord Components or Patterns when placed inside the shell.
  • Keep primary content primary. Supporting regions must not visually or semantically compete with the route's main task.
  • Allow independent region growth. Summary labels, values, descriptions, lists, and user content must wrap without requiring synchronized fixed heights.
  • Do not make visual columns semantic. Grid tracks and side-by-side placement express geometry; the chosen HTML landmarks express meaning.

Responsive page composition

  • Respond to useful available width. The shell may move from navigation-plus-content to stacked regions when those regions can no longer remain useful side by side.
  • Preserve source order through reflow. CSS may change tracks, wrapping, or placement, but narrow presentation must not reverse the reading or keyboard sequence.
  • Do not compress navigation or actions below useful measures. Stack or wrap relationships before labels, hit areas, or content become unusable.
  • Keep the main region fluid. Long text, tables, lists, forms, and nested Patterns should negotiate available width without forcing the shell itself to create horizontal page scrolling.
  • Avoid device-named shell variants. The relationship changes because available space and content require it, not because the page has become a named phone or tablet Template.

Accessibility, focus & resilience

  • Provide a reliable path to main content. The consuming application should support efficient keyboard movement to the main route content, such as a skip link where the surrounding product shell warrants one.
  • Do not move focus because regions reflow. Focus remains with the active control unless the interaction or route transition has its own established focus contract.
  • Support zoom and text enlargement. Navigation, summary regions, actions, headings, and supporting content must wrap and reflow without clipping or overlap.
  • Allow localization and long content. Do not size the shell around short English labels or fixed summary values.
  • Keep status communication scoped. Loading, error, success, and other dynamic states compose the canonical Feedback Patterns; the shell does not create a page-wide live region by default.

Application state boundary

  • Data remains application-owned. Summary values, lists, permissions, and page content come from the consuming product.
  • Authorization remains application-owned. The shell can provide a region where restricted or unavailable content is explained; it does not decide who can see it.
  • Persistence remains application-owned. No shell region implies autosave, caching, or durable state.
  • Business logic remains application-owned. The Template determines composition, not what a summary means or which action a product allows.
  • Loading and failure use existing Patterns. When route content is pending or fails, compose Loading & Progress, Status Messaging, Empty States, or other appropriate contracts rather than embedding hidden shell-specific state logic.

Theme, density & page-scale validation

The same semantic shell should remain understandable across supported themes, light and dark appearance, density settings, localization, zoom, and narrow available widths.

Theme may change expression. Density may change spacing. Neither should change landmark meaning, route hierarchy, source order, navigation scope, or the relationship between primary and supporting content.

Dashboard Shell therefore acts as the first Template-level integration proof that Foundations, Layout, Components, and Patterns can coexist as one page without requiring one-off component overrides.
