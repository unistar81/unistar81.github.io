Form Flow

Form Flow demonstrates how one bounded form moves from entry through validation, correction, submission, and a meaningful result while preserving user work and the canonical contracts of the controls and Patterns beneath it.

Workflow state contract

One form, several application-owned states

The same form composition can move through entry, correction, submission, and result states without making the Template a state machine. The consuming application decides when each state is true.

01 Entry Collect values without treating untouched input as erroneous.
02 Demonstrated state Validation / correction Preserve valid values and explain the affected field or group.
03 Submitting Prevent unsafe duplicates and compose Loading & Progress when needed.
04 Result Compose Status Messaging for success or recoverable failure.

Composition boundary

Form Flow owns the page-level relationship among form structure, validation and correction, actions, pending submission, and resulting status. It does not own the internal contract of Input, Select, Textarea, Field Group, Button, Alert, Loading Indicator, Form Layout, Form Validation, Action Groups, Loading & Progress, or Status Messaging.

The consuming application owns validation truth, submission, persistence, authorization, dirty state, server responses, retry policy, conflict handling, navigation-away protection, and the decision to treat a result as successful or failed.

Do not introduce a `dsl-form-flow` component, a Template submission API, or fake persistence merely to demonstrate the lifecycle.

Workflow lifecycle

These are states of one form workflow, not steps in a Progress Indicator. Use Multi-step Flow when the user is intentionally moving through a known ordered sequence of separate steps.

  • Entry: Present the fields and guidance required for the task without implying that incomplete input is already erroneous.
  • Validation and correction: Identify the affected field or group, explain what needs attention, and preserve the user's other values.
  • Pending submission: Keep the form context recognizable while preventing unsafe duplicate submission. Compose Loading & Progress when waiting is noticeable.
  • Success: Communicate a meaningful result through Status Messaging or the consuming workflow's next destination. Do not leave a stale editable form implying that the same submission is still pending.
  • Recoverable failure: Preserve valid user work, explain what failed, and keep an understandable retry or correction path.

Entry & field composition

  • Use visible labels and persistent supporting guidance.
  • Keep labels, controls, descriptions, and errors in canonical Form Layout relationships.
  • Group related choices with `fieldset` and `legend`.
  • Keep optional versus required meaning understandable without relying on placeholder text.
  • Preserve semantic source order as fields reflow.
  • Use a useful reading and interaction measure rather than stretching controls across the full page merely because width is available.

Validation & correction

  • Keep each error adjacent to the affected field or group and associate it programmatically.
  • Preserve entered values when validation fails.
  • Do not mark untouched fields invalid merely because the user attempted another action.
  • Focus the first invalid control only when that recovery behavior is appropriate for the workflow; do not move focus for every inline validation update.
  • If an error summary is warranted for a long form, make it supplemental to field-level correction rather than the only explanation.
  • Distinguish client constraints from application or server validation; Concord presents the correction but does not define the business rule.

Submission & pending work

  • Keep one clear primary submission action for the bounded form.
  • Prevent unsafe duplicate submission while work is pending.
  • If submission takes noticeable time, communicate that the request is still in progress through Loading & Progress.
  • Keep entered values and surrounding context available unless the product has a deliberate reason to replace the form.
  • Do not treat a spinner as proof of success or failure.
  • Cancellation during submission is application-specific; do not expose a cancel action unless the underlying operation can actually be cancelled.

Success, failure & retry

  • Use Status Messaging to communicate the result when the user remains on the same page.
  • On success, make the next state unambiguous: completed, reset for another entry, or moved to another destination.
  • On recoverable failure, preserve valid data and keep retry distinct from changing the input.
  • If server validation identifies a field-level problem, return that correction to the affected field or group rather than leaving it only in a generic failure message.
  • Do not automatically retry mutations when doing so could create duplicate or consequential operations.
  • Keep failure language actionable and specific enough to support recovery without exposing implementation details.

Actions, dirty state & leaving the form

  • Keep primary, secondary, reset, and cancel actions semantically distinct.
  • Reset should restore a known form baseline; Cancel should leave or abandon the task according to application policy.
  • Dirty-state calculation remains application-owned.
  • Navigation-away warnings should appear only when meaningful user work would otherwise be lost.
  • Do not block navigation merely because a form exists.
  • Confirmation belongs to the Confirmation Pattern when abandoning or submitting truly consequential work requires a deliberate decision.

Focus, announcements & keyboard behavior

  • Keep keyboard order aligned with semantic source order.
  • Do not move focus merely because validation text appears.
  • When submission begins, keep focus stable unless the workflow has a clear reason to move it.
  • Announce meaningful asynchronous changes politely when appropriate; do not make the entire form a live region.
  • On recoverable failure, focus should support the next useful action or correction rather than jumping to decorative status content.
  • On success, focus behavior depends on whether the page remains, resets, or navigates; that decision belongs to the consuming application.

Responsive composition & content resilience

  • Preserve field and action order at narrow widths.
  • Let labels, guidance, errors, and generated content wrap without overlapping controls.
  • Prefer intrinsic control widths and a bounded useful form measure to rigid desktop columns.
  • Stack actions when needed without reversing their semantic meaning or DOM order.
  • Support localization, text zoom, long validation messages, and fallback fonts without horizontal page overflow.
  • Keep pending and result messages readable at the same narrow widths as the editable form.

Application ownership & state integrity

  • Form data remains application-owned.
  • Validation truth and business rules remain application-owned.
  • Submission, persistence, authorization, retries, conflict resolution, and server results remain application-owned.
  • Dirty state and navigation-away protection remain application-owned.
  • Concord Patterns own the presentation and interaction relationships used to communicate those states.
  • The Template describes the complete workflow composition without becoming a state machine or data layer.

Theme, density & page-scale validation

Validate the same semantic Form Flow across supported themes, light and dark appearance, and density settings. Theme and density may change surface expression, spacing, and control compactness, but they must not change label relationships, source order, validation meaning, action hierarchy, status semantics, or application ownership.
