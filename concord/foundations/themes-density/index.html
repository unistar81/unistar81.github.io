Theme, Appearance & Density

Theme, appearance, and density are independent axes of system expression. Theme defines visual personality, appearance establishes the luminance environment, and density changes spatial character. They compose through one token contract without branching component markup.

System behavior

Expression, luminance, and space—independently controlled

Theme changes visual personality. Appearance changes the luminance environment. Density changes how much spatial room the system uses. All three axes compose without changing semantic HTML.

Theme changes expression, not meaning

A theme operates through approved token contracts. The semantic purpose of a primary action, raised surface, focus treatment, or content role remains stable even when its visual expression changes. Themes own both their normal system palette and the dark-appearance roles needed to preserve that personality when the luminance environment changes.

Appearance changes the luminance environment

Appearance answers whether the interface is operating in a light or dark environment. It remaps Semantic color roles onto theme-owned appearance roles; it does not create a second component implementation or a separate dark copy of every component.

The supported web composition is `data-theme` + `data-appearance` + `data-density`. A component continues consuming the same Semantic and Component tokens in every combination.

Density changes spatial character

Density answers a different question: how compact or spacious should the interface feel? Compact, default, and spacious modes adjust spatial dimensions such as padding, gaps, control footprint, and minimum size while preserving the same component size variant, content, interaction model, typography, stroke weight, and theme-owned shape.

A medium Button is still the medium Button whether the surrounding system is compact or spacious. Density can change its padding and resulting control footprint, but it does not replace a theme's typography, border weight, or corner-radius decisions.

The axes compose independently

Theme does not imply appearance or density. Appearance does not imply theme or density. A theme can operate light or dark, compact or spacious, without multiplying component variants. The combination is produced through the token cascade.

The web cascade contract is `base → theme → density → appearance → consumer overrides`. Appearance is intentionally later than theme so it can remap semantic luminance while retaining the active theme's System-level color personality.

High contrast is an accessibility environment, not a theme

Windows High Contrast and other forced-color environments are handled through `forced-colors: active` and CSS system colors. Concord does not replace the user's chosen palette with a branded high-contrast theme. Components preserve boundaries, focus, state, and meaning using system colors such as `Canvas`, `CanvasText`, `ButtonFace`, `ButtonText`, `Highlight`, `HighlightText`, `LinkText`, and `GrayText`.

`prefers-contrast: more` is progressive enhancement for users requesting more contrast when forced colors are not active. It is separate from both Theme and Appearance.

Override boundaries are governed

Concord validates override sources against the architectural tiers they are allowed to modify. Foundation vocabulary and semantic purpose remain stable; theme-owned System roles, appearance-owned Semantic mappings, and approved Component contracts provide controlled points of variation.
