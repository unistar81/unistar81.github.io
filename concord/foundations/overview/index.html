Foundations / Overview

Foundations

Foundations define the shared visual and behavioral language beneath Concord. Raw values become stable contracts, purpose-oriented decisions, and component-owned implementation details so the system can change expression without scattering those decisions across individual interfaces. Concord separates durable design-language contracts from the technologies used to deliver them.

Foundation architecture

The language beneath the components

Tokens provide the vocabulary. Semantic HTML and CSS provide the grammar. Governance keeps the language coherent as teams, products, themes, and delivery technologies evolve.

Components, themes, and platform outputs consume these contracts without becoming new sources of design truth.

Ownership model

One decision, four levels of meaning

Specificity increases downstream. Each tier owns a different kind of decision instead of allowing components to reach directly into raw values.

Operating principles

Stable Contracts outlive implementations

Semantic structure and token APIs remain recognizable as delivery technology changes.

Adaptive Expression can change intentionally

Themes, density, responsive behavior, and states evolve through approved contracts.

Portable Delivery technology remains replaceable

Rendering machinery consumes the design language rather than becoming its source of truth.

Foundations are contracts, not decoration

Color, typography, spacing, geometry, elevation, and motion are most useful when they become shared decisions rather than isolated styling choices. Concord separates the vocabulary available to the system from the contracts that components and layouts actually consume.

Tokens provide the vocabulary. Semantic HTML and CSS provide the grammar. Governance supplies the rules that keep those decisions coherent as the system grows, themes change, and new delivery technologies are introduced.

Ownership prevents accidental coupling

Not every reusable value should control every place where that value happens to appear. Foundation tokens provide raw vocabulary; system and semantic roles assign shared meaning; component tokens own decisions that belong to a specific implementation.

Clear ownership lets one part of the visual language change without forcing unrelated components to change with it.

Expression can change while structure stays stable

Concord's web interface architecture is web-platform-native and framework-agnostic by design. Semantic HTML, CSS, tokens, and behavioral contracts define the web design language; frameworks are delivery machinery that consume those contracts. Framework choice is a delivery decision, not a design-language decision.

On the web, teams can consume generated CSS token contracts independently, adopt the canonical semantic HTML/CSS implementation, package that implementation as Web Components, or integrate it through framework adapters. These are consumption choices around the same design-language contracts, not separate sources of truth.

The canonical token graph is platform-neutral. Concord now generates sibling CSS, Swift, and Kotlin token distributions from the same validated graph: CSS preserves authored reference relationships for the web cascade, while native outputs consume resolved build-time variants. Native token generation is a distribution capability, not a claim that Concord ships native iOS or Android component libraries, and platform compiler validation remains a separate release-readiness gate.
