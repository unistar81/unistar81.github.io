Foundations / Responsive Principles

Responsive Principles

Responsive behavior starts with the space an interface actually receives, the content it must carry, and the intrinsic behavior of its elements—not with a list of device names. Concord components are expected to remain usable as their containing width changes, while containers, grids, and page-level responsive APIs belong to the separate Layout layer.

Principle

Responsive foundation

Constraint before device category

Concord treats responsive behavior as a relationship between available width, intrinsic content, and the layer that owns the layout—not as a fixed list of phone, tablet, and desktop modes.

Mobile-first, not device-first

Concord starts from a usable narrow-space baseline and progressively enhances the interface as more space becomes available. In that sense, the system is mobile-first. Responsive behavior is not tied to phone, tablet, or desktop categories; it responds to content, intrinsic behavior, and the space the interface actually receives.

Mobile-first establishes the baseline; available space determines the behavior.

For Product Design, the narrow-space baseline establishes the hierarchy, relationships, and essential content that must remain understandable and usable under constraint. For Engineering, it means implementing that resilient baseline first and enhancing the composition only when additional space makes a different relationship useful.

Available width is the real constraint

Viewport width and component width are not the same thing. A component can be narrow inside a wide page because it lives in a constrained region, and a component can receive generous space inside a smaller application shell.

Responsive decisions should therefore be tested against the containing space the component actually receives rather than inferred from a phone, tablet, or desktop label.

Prefer intrinsic behavior before branching

Where the component contract allows it, content should participate in sizing. Natural width, wrapping, logical properties, flexible distribution, and intrinsic layout behavior should solve the common case before a breakpoint is introduced.

A breakpoint is justified when behavior genuinely has to change—not merely because a familiar device width has been crossed.

Content resilience is responsive behavior

A component that survives only its ideal demo copy is not resilient. Long labels, expanded descriptions, unbroken strings, text enlargement, constrained containers, and different theme/density combinations all expose whether the layout can absorb real content variation.

Responsive validation therefore includes content pressure as well as geometric pressure.

Components and Layout own different responsibilities

Components own their semantic structure, states, accessibility, internal relationships, and content resilience. Layout owns relationships between components and regions: containers, columns, gutters, page structure, and higher-level spatial composition.

Keeping those responsibilities separate lets the same component remain stable as future Layout APIs evolve around it.
