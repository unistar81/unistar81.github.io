Foundations / Accessibility

Accessibility Foundations

Accessibility is a system constraint, not an optional component variant. Concord starts with native HTML semantics, preserves browser interaction models where possible, and uses shared contracts for focus, color, motion, state, and content resilience so accessibility survives visual themes and component evolution.

Accessibility foundation

Accessible by construction, not by exception

Semantics, keyboard behavior, focus, naming, state, adaptation, and validation are parts of the system contract. Styling can change without removing those foundations.

Native semantics

Keep the browser contract, then add the design language

Concord should not recreate behavior the platform already provides. Native semantics establish meaning and interaction before tokens or component styling change the visual expression.

Validation model

Accessibility requires more than one kind of evidence

Semantics carry behavior before styling begins

Native HTML establishes meaning and interaction for many controls before a design system adds any visual treatment. Concord should preserve those browser contracts wherever the platform already provides the appropriate role, state, naming relationship, and keyboard model.

The design language can then change color, typography, spacing, geometry, and other expression without requiring the component to recreate semantics it could have kept.

Accessible identity is relational

A control is understood through relationships: its visible label supplies a name, supporting text adds context, related controls expose grouping, and keyboard focus identifies where interaction currently lives.

Those relationships matter more than isolated ARIA attributes. Focus and state also need durable visual and programmatic cues so a theme can change expression without changing meaning.

Adaptation must preserve the information

Text enlargement, zoom, constrained width, reduced motion, translation, and high-contrast environments can change how an interface is expressed. The information, destination, control relationship, and state must remain understandable after those adaptations.

Forced colors are a system accessibility environment. Concord provides a shared forced-colors contract for component boundaries, focus, state, disabled treatment, links, fields, overlays, and other custom-rendered UI, while component-specific rules remain responsible for specialized geometry such as checks, switches, progress, and range controls. Coverage is verified in browser tests rather than inferred from normal-theme contrast.

Accessibility is validated through layered evidence

Automation can catch many detectable violations, but it cannot prove the full interaction. Browser-level testing is needed for keyboard flow, focus, dialogs, state changes, zoom, and responsive pressure. Assistive-technology behavior and whether the experience is actually understandable still require human evaluation.

Accessibility therefore comes from the agreement between semantics, naming, interaction, focus, visual state, adaptation, and observed behavior—not from the presence of one attribute or one automated test.
