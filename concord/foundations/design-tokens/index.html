Foundations / Design Tokens

Design Tokens

Design tokens turn design decisions into durable contracts between visual language and implementation. Concord separates raw vocabulary from shared roles, semantic intent, and component ownership, then distributes the same validated graph through platform-appropriate contracts without creating separate sources of design truth.

Why tokens exist

Hard-coded values are easy to add and difficult to govern. Once color, spacing, typography, motion, and component-state decisions are repeated directly in implementation, their meaning becomes distributed across the codebase. Changing the visual language then becomes a search-and-replace problem instead of a system-level decision.

Concord gives those decisions stable names and explicit relationships. Components consume contracts rather than memorizing raw values, making the system easier to inspect, theme, validate, and evolve.

From vocabulary to ownership

The token model moves toward increasing specificity. Foundation tokens define reusable vocabulary such as color, spacing, typography, radius, stroke, shadow, and motion. System tokens promote selected values into shared design-system contracts. Semantic tokens describe purpose rather than appearance. Component tokens own implementation decisions that belong to a specific component.

The tier matters because it identifies ownership. A primary action can remain a primary action when a theme changes color, typography, border treatment, radius, or another approved expression; the consuming component does not need to invent a second contract.

References become runtime contracts

A reference is more meaningful than a duplicated value. When a Button background references `semantic.color.action.primary`, the relationship explains why the value exists and preserves that intent while upstream decisions change.

The canonical graph remains structured source data. Concord validates and prepares that graph once for distribution. The authored, reference-bearing view drives CSS so intentional `var(...)` relationships remain part of the web runtime contract; resolved views drive generated native token sets. Generated output remains downstream evidence, never a second source of truth.

var(--dsl-semantic-color-action-primary)

One graph, platform-specific contracts

Web, iOS, and Android consume sibling outputs from the same token engine. The canonical token path stays stable while each platform receives naming, type representation, serialization, and file organization appropriate to that environment. The generated platform map connects each canonical path to the real CSS, Swift, and Kotlin symbols that exist in the repository.

Native generation does not sit upstream of CSS and does not create a second resolver. Removing a native distribution target does not change the canonical graph or the public web runtime contract.

Portability is explicit

Not every web value has a meaningful native equivalent. Relative units such as `em` or `vw` require context that cannot be inferred safely from a token type alone. When no reviewed native mapping exists, Concord records the portability limitation explicitly and withholds a misleading native accessor instead of inventing a conversion.

The same principle applies to platform APIs that cannot preserve a canonical decision losslessly: preserve the design value, introduce a Concord-owned representation where appropriate, or mark the platform mapping unsupported. Delivery APIs do not redefine the design language.

Validation governs change

Validation protects the dependency direction of the system, catches invalid references, and constrains which tiers an override may change. Theme and density pass through the same preparation and resolution machinery for every distribution target, so platform output does not acquire a parallel theme engine.

Theme and density solve different problems. Theme can change visual expression—palette, typography, elevation, geometry, border treatment, and approved component decisions—while density changes spatial character. Keeping those axes independent allows either one to evolve without changing the semantic structure of the interface.
