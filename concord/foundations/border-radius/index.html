Foundations / Border & Radius

Border & Radius

Borders and corner geometry give surfaces definition without becoming decoration for its own sake. Concord keeps raw radius and stroke values reusable, then lets semantic and component contracts decide where a boundary exists, how strongly it should read, and what geometry belongs to that interface.

Visual foundation

Boundaries and geometry with clear ownership

Radius, stroke, and border color are independent decisions. Concord combines them downstream only where a surface, state, or component actually needs a boundary.

Geometry is a vocabulary before it is a component

Foundation radius values describe available corner treatments: small, medium, large, and effectively circular or pill geometry. Stroke tokens likewise provide a compact width vocabulary and supported line styles.

Those values become meaningful only when another layer chooses them for a control, surface, focus treatment, or component shape.

Borders communicate structure and state

A border can separate adjacent surfaces, define an interactive control, reinforce selection, or make focus visible. Those are different responsibilities even when they happen to use the same raw stroke width.

Color roles such as subtle, default, strong, and focus provide semantic context while geometry and width remain separate decisions. This separation lets themes change visual expression without collapsing every boundary into one treatment.

Components own their geometry

Button, checkbox, toggle, pill, tooltip, and other components can consume different radius and stroke contracts because their shapes serve different purposes. A pill radius is appropriate for a toggle track or selectable pill, while a smaller radius may preserve a more architectural control shape.

A holistic theme may intentionally change approved component geometry while the component API and semantic HTML remain stable. Foundation values themselves remain reusable vocabulary rather than a theme-specific component specification.
