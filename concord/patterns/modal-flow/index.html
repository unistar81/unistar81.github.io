Modal Flow

A modal flow isolates a focused task or decision when the surrounding interface must become temporarily unavailable. It coordinates entry, focus, task structure, dismissal, actions, validation, and recovery while preserving the native dialog contract.

Composition boundary

Modal Flow owns the task orchestration around modality, not the Modal component mechanics or the product operation. Modal owns the native `dialog`, modal top layer, inert background, focus containment, Escape behavior, explicit close anatomy, viewport-constrained surface, and focus return. The consuming application owns task data, business rules, persistence, pending state, failure, and success.

Confirmation owns whether a consequential action needs a deliberate decision point. A Confirmation may be presented in a Modal when blocking the surrounding interface is warranted, but Confirmation and Modal are not synonyms. Form Validation owns field and group correction. Action Groups owns action hierarchy. Status Messaging communicates meaningful results after or during the workflow.

When modality is warranted

  • Use Modal only when the surrounding interface must pause. The user should need to complete, abandon, or explicitly exit the focused task before safely returning to the background context.
  • Prefer Popover for contextual non-modal disclosure. If users can continue interacting with the surrounding page while the surface is open, a Modal is usually too strong.
  • Do not use Modal merely to make content feel important. Supplemental information, read-only detail, and routine help should remain inline or use the appropriate disclosure pattern.
  • Keep the task bounded. A Modal works best for a compact task with a clear entry and exit. Large multi-step workflows, extensive editing, or navigation-heavy work usually deserve a page-level flow.
  • Avoid stacked or nested modals. If the task develops another decision, prefer changing the current Modal state, returning to the parent workflow, or using an inline decision within the same surface rather than layering dialogs.

Entry, focus & keyboard

  • Open through the canonical invoker. Concord uses the native dialog command relationship where supported and the framework-neutral dialog enhancement as the compatibility fallback. Patterns should not add their own click-to-`showModal()` script.
  • Choose initial focus deliberately. A short, self-explanatory form may focus its first meaningful control. A long or structurally complex dialog may focus its heading with `tabindex="-1"`. A consequential confirmation may focus the conservative cancel path. Do not automatically focus the primary commit action.
  • Let native modality contain focus. `showModal()` moves the dialog into the top layer and makes the rest of the document inert. Do not add a second focus-trap implementation.
  • Let Escape provide the ordinary cancel path. Do not suppress native Escape merely to force completion. If abandoning the task would lose meaningful work, design explicit recovery or confirmation behavior rather than silently discarding changes.
  • Return focus to the invoker. Native dialog behavior restores focus to the control that opened the Modal. If that control no longer exists after completion, the consuming application must choose a logical replacement focus target.

Task structure & actions

  • Give every Modal a visible programmatic title. Associate the heading through `aria-labelledby`. Use `aria-describedby` for concise supporting text when reading that description with the title improves orientation.
  • Keep an explicit close control. The close action is non-commit and should have an accessible name that identifies the dialog it closes.
  • Keep task controls semantically ordinary. Inputs, checkboxes, radios, links, and other nested components retain their canonical behavior; Modal does not redefine them.
  • Use one clear primary task action. Compose actions through the normal Button and Action Groups hierarchy. Labels should state the result, such as "Save preferences", rather than generic "OK".
  • Keep cancel, close, and Escape semantically consistent. They should all abandon the current Modal task without accidentally committing its primary action.
  • Use native dialog return values for close intent, not business truth. A `method="dialog"` form can report values such as `save` or `cancel`; the consuming application still decides whether the requested operation actually succeeds.

Validation, pending & outcomes

  • Keep validation with the affected controls. If a field or group is invalid, use Form Validation inside the Modal and keep the task open so the user can recover.
  • Prevent duplicate commitment while work is pending. The consuming application owns pending state and may temporarily constrain the initiating action when repeated activation would be unsafe.
  • Do not close before recoverable failure is understood. When saving fails and the user can correct or retry within the task, keep the Modal open and present the relevant error or Status Messaging in context.
  • Close on successful completion when the task is finished. Return focus to the invoking workflow and use Status Messaging there when users benefit from confirmation of the result.
  • Preserve entered state across recoverable errors. Validation or server failure must not erase the work users need in order to retry.

Responsive & long-content behavior

  • Keep the Modal inside the dynamic viewport. The canonical surface clamps to available width and height so close and task actions remain reachable.
  • Scroll the content region, not the page behind the Modal. Long content should remain bounded while the dialog heading, close path, and action region stay usable.
  • Allow labels and actions to wrap. Localized or expanded text must not force horizontal page scrolling or hide essential actions.
  • Keep modality understandable at narrow widths. The same semantic source order and action hierarchy should remain intact as the surface compresses.
  • Do not turn a long workflow into a Modal simply because the surface can scroll. Scrolling is resilience for a focused task, not permission to move page-sized work into a dialog.
