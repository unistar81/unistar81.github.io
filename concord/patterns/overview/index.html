Where patterns fit

Patterns sit between reusable interface contracts and page-level composition. The boundary is deliberate: components own the interface contract, patterns own relationships among contracts, and templates own page-level arrangement.

Patterns reuse contracts; they do not fork them. A Button inside an Action Group remains the canonical Concord Button, and an Input inside Form Validation remains the canonical Concord Input.

Examples:

  • Button. Action Groups define primary and secondary action hierarchy around the canonical action contract.
  • Input. Form Layout and Form Validation define the control's relationship to labels, guidance, error communication, and actions.
  • Modal. Modal Flow and Confirmation define how the focused dialog contract participates in a larger decision flow.

How a pattern is composed

Patterns combine canonical components with Concord Layout and the semantic, content, and interaction rules that govern their relationship.

Concord Layout owns spatial relationships and responsive composition. Components retain their internal contracts. The pattern owns the relationship between them: role, ordering, hierarchy, communication, and behavior across the interaction.

Patterns may compose other patterns when doing so preserves their existing contracts and avoids duplicating guidance.

Patterns can describe required interaction and state relationships, but they do not own product business logic, data fetching, routing, or domain-specific rules. Those responsibilities remain with the consuming application and its chosen framework or application architecture.

What a pattern defines

A pattern is useful when the relationship between existing pieces needs stable guidance, not simply because the same arrangement appears more than once.

Accessibility is cross-cutting. Semantic relationships, reading and source order, keyboard and focus behavior, status communication, motion, and non-color cues are part of the pattern contract rather than a separate optional layer.

  • Composition. Participating components, their roles, meaningful source order, semantic grouping, and hierarchy.
  • Interaction. Keyboard and focus expectations, state transitions, and the behavior that coordinates the participating contracts.
  • Communication. Labels, instructions, status, error relationships, and other content needed to make the interaction understandable.
  • Responsive behavior. How the composition adapts through Concord Layout while preserving useful content, semantics, and DOM order.
  • Usage boundaries. When to use the pattern, when not to use it, and which responsibilities remain owned by the underlying components or consuming application.

Pattern maturity

Concord uses pattern status to distinguish supported guidance from documented direction as the library evolves.

A pattern becomes Implemented when its required Concord contracts have shipped and its composition, accessibility, responsive behavior, and appropriate regression coverage are supported.

  • Implemented. Supported pattern guidance backed by shipped Concord component and Layout contracts.
  • Planned. Architectural direction is documented, but the pattern contract is not yet supported. Planned does not imply that a new component or API will be created.

Pattern families

Concord groups patterns by the recurring user problem they solve rather than by the component that happens to implement them.

  • Forms. Collecting, grouping, and validating user input.
  • Actions. Establishing action hierarchy and consequential decisions.
  • Feedback. Communicating status, progress, and system outcomes.
  • Disclosure. Revealing supplemental or focused content with the appropriate interaction model.
  • Content & Collections. Finding, presenting, and navigating sets of information.
