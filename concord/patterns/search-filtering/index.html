Patterns / Content & Collections

Search & Filtering

Search and filtering help users reduce a collection through free-text query, structured criteria, or both while keeping the active criteria, result state, and recovery path understandable. Concord composes existing controls for this work rather than introducing a monolithic Search component.

Composition boundary

Search & Filtering owns the relationship among query controls, structured criteria, applied state, result feedback, and the collection being reduced; it does not own product search logic. Input owns text entry. Selectable Pill, Select, Checkbox, and other controls retain their canonical selection semantics. List Item, Card, table, or another collection presentation owns each result's rendering. Pagination owns movement through a divided result set.

The consuming application owns query syntax, matching and ranking, server requests, caching, routing, authorization, result data, and persistence. Empty States owns the recovery presentation when no matching results remain. Loading & Progress communicates meaningful waiting while an asynchronous result set is changing.

Query, filters & sorting

  • Use search for free-text intent. A search query commonly matches titles, descriptions, identifiers, or other text-oriented fields. Keep a visible label even when a search icon is present.
  • Use filters for structured dimensions. Type, status, owner, date range, or similar known attributes are filter criteria rather than free-text search.
  • Compose query controls through Form Field. Search & Filtering may compose a labelled Input, but Form Field owns the local label, control, and supporting-text stack. The Pattern owns query/filter/result relationships and field measure, not another field-spacing implementation. Configure that measure through the existing public Field and Input width properties rather than overriding component internals.
  • Keep independent filters independently selectable. Selectable Pills retain native checkbox semantics; do not visually present mutually exclusive choices as independent Pills.
  • Keep sorting conceptually separate. Sort order changes how the same result set is arranged; it does not reduce the set. A sort control may live near filters without being described as a filter.
  • Do not invent a system query language. Tokenization, fuzzy matching, operators, synonyms, spelling correction, and ranking are product/search-service decisions unless Concord later defines an explicit contract.

Applying & clearing criteria

  • Choose an application model deliberately. Search may execute on explicit submission or after a considered debounce; filters may apply immediately or through an explicit Apply action. Use a predictable model rather than mixing behaviors arbitrarily within one group.
  • Keep the applied state visible. Users should be able to determine which query and criteria produced the current collection without reopening hidden controls.
  • Provide a clear recovery path. When criteria can accumulate, provide a way to remove individual criteria or clear the relevant group without erasing unrelated product state.
  • Reset dependent navigation when criteria change. A materially changed query or filter set should normally return a paginated collection to its first valid page rather than leaving users on a now-invalid later page.
  • Preserve meaningful shareable state when appropriate. For collections users may bookmark, share, or revisit, applications should consider encoding stable query, filter, sort, and page state in the URL. Concord does not prescribe a routing format.

Results & announcements

  • Keep result feedback close to the collection. A count or concise summary should identify the current result state without forcing users to infer whether criteria took effect.
  • Announce meaningful asynchronous result changes politely. A stable `role="status"` or equivalent live region may report the resulting count after an update. Do not announce every keystroke or every transient loading frame.
  • Do not move focus when results refresh. Keep keyboard focus on the control the user is operating unless the workflow explicitly requires a different recovery target.
  • Preserve the collection contract while data changes. Result rows or cards retain their own semantics; loading, filtering, or sorting must not turn them into a new Search-specific component.
  • Distinguish no matches from an empty collection. Zero matches after criteria are applied is a Search & Filtering recovery condition; a collection that has no content at all is a different Empty State.

Async, loading & stale results

  • Represent real waiting through Loading & Progress. When a remote query takes noticeable time, keep useful context visible and mark the affected result region busy when that relationship matters.
  • Prevent stale responses from replacing newer intent. Applications should cancel, ignore, or reconcile out-of-order requests so an older response cannot overwrite a newer query or filter state.
  • Avoid result flicker for trivial work. Do not flash a loading treatment for operations that complete immediately, but never delay feedback long enough that the interface appears unresponsive.
  • Keep existing results only when their status is clear. If stale results remain visible during a refresh, communicate that they are being updated rather than presenting them as the confirmed result of the new criteria.
  • Handle failure as recoverable workflow state. A failed search request should preserve the query and filters needed to retry and should not masquerade as "0 results."

Responsive & accessibility behavior

  • Preserve semantic source order as controls wrap. Narrow layouts may stack the query, filters, and result summary without changing their reading or keyboard order.
  • Keep active criteria discoverable on small screens. If a larger filter set moves behind Popover or Modal disclosure, the trigger should communicate that filters are applied and the disclosed controls must retain their normal semantics.
  • Do not shrink controls to keep one row. Let filter controls wrap or restructure instead of compressing labels, hit targets, or readable input measure.
  • Group related criteria semantically. Use `fieldset` and `legend` when a set of controls answers one filter question; visual proximity alone does not create a group relationship.
  • Keep labels resilient. Query labels, filter names, result summaries, and applied criteria must tolerate localization and longer product terminology without obscuring controls.

Relationship to collection navigation

  • Filter first, then paginate the resulting set. Pagination represents the current reduced collection rather than the unfiltered source collection.
  • Keep result count and page location consistent. When Pagination is present, its summary and current page must describe the same query/filter result state shown by the collection.
  • Do not treat infinite loading as a filtering requirement. Pagination, load-more, virtualized lists, and continuous scrolling are collection-navigation decisions that may compose with this Pattern but are not owned by Search & Filtering.
