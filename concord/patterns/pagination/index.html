Patterns / Content & Collections

Pagination

Pagination divides a known result set into navigable pages while keeping the current location, collection context, and destination semantics understandable. The Pattern composes Concord's canonical Pagination control with the collection it navigates; it does not create a second pagination implementation.

Composition boundary

Pagination owns the relationship among a paged collection, result-range context, page destinations, and page-change recovery; the Pagination component owns the navigation control itself. The component supplies the native `nav` landmark, list structure, Link-based destinations, non-interactive current-page semantics, boundary treatment, ellipses, and optional range summary.

Search & Filtering owns the query, filters, and sort state that define the result set. Empty States owns the known-zero state. Loading & Progress owns meaningful waiting while another page is being fetched. The consuming application owns page size, total-count truth, route construction, page-window calculation, data fetching, caching, authorization, and persistence.

Choose the navigation model

  • Use numbered pages when stable location matters. Numbered pagination is useful when users benefit from jumping within a known result set, returning to a prior page, sharing a location, or understanding approximate position in a collection.
  • Use Previous/Next when an exact page count is unavailable or unhelpful. Cursor-based data, rapidly changing feeds, or sequential browsing may not have a trustworthy total. Do not fabricate numbered pages from an unstable count.
  • Do not use Pagination for step-based workflows. Account, Review, and Complete belong to Progress Steps or another workflow model; page numbers represent collection location, not task progress.
  • Treat load-more and infinite scrolling as different collection-navigation models. They may be valid product choices, but they do not become Pagination merely because more records are fetched.
  • Avoid pagination for trivially small collections. Do not add navigation controls when all useful content can be presented clearly in one bounded collection.

Destinations, current page & history

  • Use real destinations for navigable pages. Previous, Next, and numbered destinations remain links so users can open them in a new tab, copy them, and use browser history as expected.
  • Keep the current page non-interactive. Identify it with `aria-current="page"`; do not link the user to the location they already occupy merely for visual consistency.
  • Preserve collection-defining state in destinations. Query, filters, sort order, page size, and other stable state that defines the collection should survive page navigation when the product exposes that state through URLs.
  • Let browser history remain meaningful. Back and Forward should restore understandable collection locations. Client-side routing should preserve the same destination model rather than replacing links with button-only navigation.
  • Use a context-specific landmark name when needed. If a page contains more than one pagination landmark, name each one for the collection it controls, such as "Search results pagination."

Range, totals & page windows

  • Keep the visible range consistent with the data shown. A summary such as "Results 101-150 of 1,238" must describe the same page and total represented by the collection and navigation.
  • Do not claim a total the application does not know. Omit or rephrase the summary when counts are estimated, delayed, or unavailable.
  • Keep large page ranges compact. Show a useful window around the current location plus meaningful boundaries rather than rendering every page number in a very large result set.
  • Use ellipses as non-interactive omission markers. Ellipses indicate skipped page ranges; they are not destinations unless the component later defines an explicit jump interaction.
  • Keep window calculation application-owned. Concord defines how the resulting Pagination items are presented, not the product algorithm that selects which page numbers appear.

Relationship to search & filtering

  • Paginate the reduced result set, not the source collection. Query, filters, and sort determine the collection first; Pagination divides that resulting set.
  • Reset to a valid page when criteria materially change. A new query or filter set should normally return to page 1 rather than preserving a page number that may no longer exist.
  • Preserve criteria in every page destination. Navigating to page 4 must not silently drop the query, filter, sort, or other collection context that produced page 4.
  • Remove Pagination when there are no pages to navigate. A known-zero result belongs to Empty States, while a single-page result normally needs no page navigation.
  • Keep result count, range, and current page synchronized. These are different expressions of the same collection state and must not drift during asynchronous updates.

Data stability, page size & selection

  • Keep ordering deterministic across pages. When the product uses offset or numbered pagination, apply a stable sort and a deterministic tie-breaker so records with equal primary sort values do not unpredictably move between adjacent pages.
  • Expect mutable datasets to shift. Inserts, removals, permission changes, and background updates can change totals and move records between pages. Do not promise that a page number is a permanent absolute position when the underlying collection is changing.
  • Expose page size only when it serves a real task. A page-size control is a separate collection preference, not part of the Pagination navigation itself. If users change it, return to a valid page and keep the resulting range, total, and destinations synchronized.
  • Define selection scope across pages explicitly. In selectable collections, distinguish "select this page" from "select all matching results." Page navigation must not silently broaden a selection from visible records to the entire result set.
  • Preserve or clear cross-page selection deliberately. If selected items remain selected while users navigate pages, keep the scope and count understandable. If navigation clears selection, communicate that product rule before users commit bulk work.

Loading, focus & scroll

  • Treat page activation as navigation, not a button action. Full document navigation can use normal browser behavior. In-place application routing must preserve equivalent semantics.
  • Keep meaningful loading scoped to the collection. When another page is fetched asynchronously, Loading & Progress may mark the affected result region busy without replacing the Pagination contract.
  • Prevent stale page responses from replacing newer navigation. Applications should cancel, ignore, or reconcile out-of-order requests so a slower response for page 3 cannot overwrite a later request for page 4.
  • Handle focus deliberately when content is replaced in place. If client-side rendering removes the activated link or replaces the Pagination control, move focus to a logical result-region heading or another stable recovery target. Do not send focus to the top of the document by default.
  • Keep scrolling predictable. A full navigation may restore browser/document position according to the product routing model. In-place pagination may return the collection to its start when that improves orientation, but focus and scroll should describe the same destination rather than moving independently.
  • Announce meaningful range changes, not every rendering step. If an in-place update needs assistive-technology feedback, announce the resulting range or collection state through the owning result-status relationship instead of making the Pagination landmark a live region.

Responsive & boundary behavior

  • Let the canonical component wrap before inventing another mobile control. Preserve link semantics, current-page meaning, and source order as available width narrows.
  • Do not remove page context solely because the viewport is narrow. A smaller visible window may be appropriate, but responsive presentation must not change what Previous, Next, current page, or ellipses mean.
  • Keep boundary controls understandable. At the first page, Previous may remain visible but non-interactive; at the last page, Next may do the same. Do not provide dead links to impossible destinations.
  • Preserve usable target sizes and readable labels. Do not compress page links below the component's interaction contract merely to keep one row.
  • Keep localization resilient. Previous/Next labels, summaries, and accessible landmark names must be allowed to grow without causing horizontal page overflow.
