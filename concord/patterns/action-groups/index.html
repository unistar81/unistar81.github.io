Patterns / Actions

Action Groups

Action groups establish clear priority among related actions and preserve that hierarchy as labels wrap, themes and density change, and available width narrows.

Composition boundary

Action Groups owns the relationship between actions, not the Button contract. Button owns each control's semantics, states, styling, focus behavior, and public configuration. This pattern owns priority, adjacency, ordering, and responsive composition between those controls.

The consuming application still owns what each action does, whether work is pending, and the resulting success or failure. Confirmation owns the deliberate pause before a consequential action when one is warranted. Menu may contain lower-frequency peer actions when action count or available space makes overflow appropriate, but it does not replace the primary action or the only recovery path.

Establish hierarchy

  • Use one primary action per decision region. Give the action that advances or commits the current task the clearest emphasis. A page may contain more than one region, but each local decision should have an understandable priority.
  • Use secondary actions for supporting or alternative paths. Secondary does not mean unimportant; it means the action should not compete visually with the primary path.
  • Do not make every action primary. Equal visual emphasis implies equal priority. When several actions truly are peers, use the same supported Button treatment instead of manufacturing false hierarchy.
  • Keep the visible set focused. When lower-frequency actions accumulate, consider the canonical Menu pattern/component for appropriate overflow. Keep the primary action and essential cancel, back, or recovery paths directly available.
  • Hierarchy is not a measure of danger. A destructive or consequential action is not automatically the primary action. Use Confirmation when the workflow requires a deliberate pause before commitment.

Ordering & labels

  • Write labels for the action result. Prefer specific verb-led labels such as "Save changes" or "Create account" over generic labels such as "OK" or "Submit" when the result can be named more clearly.
  • Keep source, reading, focus, and visual order aligned. Do not use CSS ordering to reverse actions at a breakpoint. If a product adopts a platform-specific ordering convention, author the DOM in that order.
  • Keep cancel and recovery paths understandable. Do not visually bury the only way to back out of a decision, and do not hide an essential recovery action in overflow.
  • Do not add group semantics automatically. Adjacent Buttons do not require `role="group"` merely because they share a visual row. Add an accessible group name only when grouping itself communicates useful meaning.
  • Keep unrelated actions separate. Spatial proximity implies relationship; actions that affect different tasks or scopes should not be presented as one group simply to align them.

Responsive composition

  • Keep Buttons at intrinsic width by default. Let labels and the canonical Button sizing contract determine control width instead of stretching every action to the container.
  • Wrap rather than compress. When a horizontal group no longer fits, preserve readable labels, hit targets, and logical order. The existing action composition may wrap or stack without changing Button semantics.
  • Preserve hierarchy when the layout changes. Primary and secondary treatments remain meaningful whether the group is one row or multiple lines.
  • Design for long and localized labels. Allow supported Button wrapping where necessary and avoid layouts that depend on short English labels.
  • Do not reverse priority at narrow widths. Responsive layout can change spatial arrangement, not the meaning or source order of the actions.

State & consequences

  • Disabled state belongs to the Button; the reason belongs to the workflow. Use a disabled action only when temporary unavailability is meaningful and the user can understand what is required. Do not use disabled styling as a substitute for Form Validation feedback.
  • Pending work remains application state. Prevent duplicate submission or activation while the initiating operation is pending when repeated activation would be unsafe. Keep the initiating action in a predictable location, and use Loading & Progress or Status Messaging when the workflow needs explicit progress or completion feedback.
  • Confirmation is selective. Routine reversible actions should execute without unnecessary confirmation. Compose with the Confirmation pattern when the consequence genuinely warrants a deliberate pause.
  • Preserve native keyboard behavior. Each Button remains independently focusable and activatable. Do not add roving focus or custom arrow-key behavior to an ordinary action group.
  • Themes may change appearance, not priority. Primary and Secondary may look different across themes, but the hierarchy must remain understandable in every supported theme and density.
