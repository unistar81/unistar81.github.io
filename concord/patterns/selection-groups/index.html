Selection Groups

Selection groups turn related options into one understandable question while preserving native control behavior, the intended selection model, and meaningful source order.

Composition boundary

Selection Groups owns the relationship between choices, not the behavior of each control. Form Field Group owns the semantic `fieldset`, `legend`, shared description, and group-level state. Radio, Checkbox, and Selectable Pill retain their canonical component contracts. This pattern decides which selection model fits the question and how those existing contracts work together.

Do not introduce a new selection component merely because several controls appear together. Group controls when they answer one shared question or decision.

Choose the selection model

  • Radio: one choice from a finite set. Use radios when the choices are mutually exclusive. Keep every option in the same native `name` group. Do not reproduce radio behavior with checkboxes, buttons, or pills.
  • Checkbox: zero or more independent choices. Use checkboxes when each option can be selected independently. A single standalone checkbox does not need a Field Group unless it participates in a larger shared question.
  • Selectable Pill: compact independent selection. A selectable pill retains checkbox semantics while changing the visual treatment. Use it for compact filters, tags, or similar independent selections; do not use pills to disguise a mutually exclusive radio decision.
  • Toggle: immediate binary setting. Use Toggle when changing the control represents an immediate on/off setting. Use Checkbox when the choice belongs to a form or batch of changes submitted later.

Group structure

  • Name the question with a legend. When related controls answer one question, use the canonical Form Field Group so the native `fieldset` and `legend` communicate that relationship.
  • Keep shared guidance at the group level. Associate instructions or descriptions that apply to every option with the Field Group. Keep option-specific descriptions with the individual Radio or Checkbox.
  • Keep option labels concise and distinct. The legend provides the question; each control label should identify only that answer.
  • Preserve meaningful source order. DOM, reading, focus, and visual order should agree. Responsive layout must not reorder the choices.
  • Do not group unrelated controls for visual alignment. Semantic grouping follows the question being answered, not the appearance of neighboring controls.

Interaction & responsive behavior

  • Preserve the native radio keyboard model. Arrow keys move among radios in the same native group; do not add custom roving focus or duplicate that behavior in JavaScript.
  • Keep checkboxes and pills independently operable. Each remains a native checkbox and retains its normal focus and Space-key behavior.
  • Stack by default. Vertical presentation is the safest default for scanning and wrapping. Use a horizontal arrangement only when labels are short, relationships remain obvious, and every option stays usable as available width narrows.
  • Wrap rather than compress. When a horizontal group no longer fits, preserve readable controls and logical source order instead of shrinking hit targets or labels.
  • Do not change semantics at a breakpoint. A Radio remains a Radio and a Checkbox remains a Checkbox when the visual composition changes.

Validation & state

  • Validate the question at group level. When a requirement applies to the complete choice set, keep one corrective message with the Field Group instead of presenting every option as a separate failure.
  • Radio required means one choice is required. Preserve the native radio group and use Form Validation for the feedback-and-recovery behavior after a failed attempt.
  • Default selections must represent real state. Preselect an option only when it reflects an existing user choice or a product default that can be safely assumed. Do not use a preselected choice to steer consent, optional enrollment, or preference decisions.
  • Provide an explicit empty choice when needed. If users must be able to return a mutually exclusive decision to no selection, include an explicit option such as "No preference." Native radio groups do not return to an unselected state after the user makes a choice.
  • Checkbox minimums are product rules. Requirements such as "choose at least one" or "choose up to three" belong to the consuming application; return failures through the same group-level validation relationship.
  • Disable deliberately. Disable the whole `fieldset` when the complete question is unavailable. Disable an individual option only when that specific choice is unavailable, and explain the reason when it is not obvious.
  • Indeterminate is not a third answer. Use an indeterminate Checkbox to represent a partial aggregate state such as "some items selected," not as another user-selectable value.
