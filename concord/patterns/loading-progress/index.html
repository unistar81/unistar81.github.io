Patterns / Feedback

Loading & Progress

Loading and progress communicate work that has started but has not yet produced its final result. The pattern selects the feedback model that matches what the application actually knows: unknown duration, measurable completion, or position in an ordered workflow.

Composition boundary

Loading & Progress owns the waiting model and its relationship to the affected workflow, not the underlying work. Loading Indicator owns indeterminate visual status. Progress Indicator owns measurable completion through the native `progress` element. Progress Steps owns completed, current, and upcoming position in a known sequence. The consuming application owns task state, measurement, cancellation, failure, and completion.

Status Messaging takes over when the interface needs to communicate the resulting completed, failed, warning, or other post-operation condition. Do not keep a loading or progress state visible after the application has reached a meaningful outcome.

Choose the feedback model

  • Use Loading Indicator when completion cannot be measured meaningfully. An indeterminate animation communicates that work continues; it must not imply a percentage, remaining duration, or step count the application does not actually know.
  • Use Progress Indicator when completion is measurable within a known range. Provide real `value` and `max` data from the operation. Do not manufacture progress that simply advances on a timer to make waiting feel active.
  • Measure real work. Progress values should correspond to meaningful completion of the operation rather than arbitrary animation stages. Avoid percentages that move backward or stall unexpectedly unless the underlying operation genuinely changes scope.
  • Use Progress Steps for position in an ordered workflow. Steps communicate where the user is in a sequence such as Account, Details, Review, and Complete. They are not a substitute for measurable task completion.
  • Do not combine models merely for visual richness. Use the model that answers the user's current question: "Is work happening?", "How much is complete?", or "Where am I in the process?"
  • Change models only when knowledge changes. An operation may begin indeterminate and later become measurable. If the application gains reliable progress data, transition to determinate progress without implying that earlier progress was known.

Scope & continuity

  • Keep feedback near the work it represents. A local refresh should normally communicate within that region rather than blocking or covering the entire page.
  • Mark the affected region busy when that relationship matters. The consuming application may use `aria-busy="true"` on the region whose content is being updated, then return it to `false` when the update completes. The indicator itself does not replace that relationship.
  • Keep essential waiting status announceable. `aria-busy="true"` may defer assistive-technology announcements for changes inside the busy region. When users need an immediate loading announcement, keep the status outside that busy subtree or otherwise structure the relationship so the busy state does not suppress the status message.
  • Preserve useful context while work continues. Do not remove stable labels, surrounding content, or navigation merely to make room for a spinner when those elements remain valid.
  • Avoid unnecessary layout shifts. When replacing content during a known loading transition, preserve a stable region where practical so status changes do not repeatedly move nearby controls.
  • Do not block unrelated interaction. Disable or constrain only the controls and regions whose state would become unsafe or inconsistent while the operation is pending.

Announcement, focus & motion

  • Give indeterminate loading a meaningful accessible status. The animated graphic remains decorative; the visible or accessible label communicates what is happening.
  • Do not move focus merely because loading starts or progress changes. Preserve the user's current keyboard context unless the workflow itself requires a new focus destination.
  • Avoid announcing every progress increment. The native Progress Indicator exposes its current value; do not layer a noisy live region over routine percentage changes unless the workflow has a specific announcement requirement.
  • Honor reduced motion. Loading Indicator animation follows the component's reduced-motion contract. Reduced motion must not remove the textual indication that work is still happening.
  • Avoid flicker for work that completes immediately. The consuming application may delay showing transient loading feedback when doing so prevents a distracting flash, but Concord does not prescribe a universal timing threshold. Never hide a delay long enough that users could reasonably think the interface has stopped responding.

Long-running work, cancellation & failure

  • Keep long-running status specific. Describe the operation, such as "Preparing report" or "Importing records," instead of using a generic "Loading" label when context is available.
  • Provide cancellation only when the operation can actually be canceled safely. Cancellation behavior belongs to the consuming application and should remain a normal Action Groups/Button decision rather than becoming Loading Indicator anatomy.
  • Do not leave users with indefinite loading after failure. When work fails, replace loading or determinate progress with the appropriate Status Messaging or recovery state.
  • Do not invent time remaining without reliable data. Estimated duration is product/application information and should be shown only when the estimate is meaningful enough to help users.
  • Preserve retry context. If a failed operation can be retried, keep the task scope and user-entered information needed for recovery.

Completion & workflow progress

  • End waiting feedback when the operation has reached an outcome. Replace it with the completed content or a relevant Status Messaging result rather than leaving a completed progress bar or spinner as stale decoration.
  • Use `aria-current="step"` for the current Progress Steps item. Completed, current, and upcoming state must remain understandable through semantics and text, not color alone.
  • Keep step labels meaningful and resilient. Progress Steps should remain readable as labels localize, the number of steps changes, or available width narrows.
  • Do not make Progress Steps interactive unless the workflow genuinely supports navigation. A status sequence is not automatically a step-navigation control.
